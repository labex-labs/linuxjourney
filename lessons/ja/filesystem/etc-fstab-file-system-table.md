ファイルシステムテーブルである `/etc/fstab` には、システムツールがマウントまたは有効化できるファイルシステム、スワップ領域、バインドマウント、ネットワークソース、そのほかの接続を記述します。エントリは起動処理に関与できますが、`noauto` などのオプション、自動マウントとの統合、サービスマネージャーの方針によって、いつ、あるいは実際にマウントされるかが変わります。

## 6 つのフィールド

一般的なエントリは、空白で区切られた 6 つのフィールドからなります。

```text
UUID=130b882f-7d79-436d-a096-1e594c92bb76 /data ext4 defaults,nosuid,nodev 0 2
```

1. **ソース**：デバイスパス、`UUID=`、`LABEL=`、ネットワークソース、そのほか対応する指定
2. **対象**：マウントポイント、またはスワップなど用途に応じて `none`
3. **種類**：ファイルシステムの種類、`swap`、`none`、または許可された自動判定の種類
4. **オプション**：マウントヘルパーと統合層が解釈する、カンマ区切りのリスト
5. **dump フィールド**：歴史的には `dump` バックアップユーティリティへの参加を制御し、一般に `0` で無効化する
6. **pass フィールド**：該当する場合に、起動時の `fsck` の順序を制御し、`0` でこの仕組みによる自動チェックを無効化する

フィールド内の空白は、スペースを `\040` とするような fstab 構文でエスケープする必要があります。フィールドの外では、`#` からコメントが始まります。

:::single-choice{#fstab-field-count} 通常の `/etc/fstab` エントリには、フィールドがいくつありますか？

::option[4 つ。]{#fstab-four-fields explanation="ソース、対象、種類、オプションの後に、dump と pass のフィールドが続きます。"}
::option[8 つ。]{#fstab-eight-fields explanation="8 は、1 つの fstab レコードの標準的なフィールド数ではありません。"}
::option[6 つ。]{#fstab-six-fields .correct explanation="従来の形式には、ソース、対象、種類、オプション、dump、pass の 6 フィールドがあります。"}
:::

## 安定したソース識別子

ローカルファイルシステムでは、`/dev/sdX` という列挙名より、ファイルシステム UUID の方が安定していることがよくあります。

```bash
$ lsblk -f
$ sudo blkid
```

`UUID=...` は、その識別子が目的のファイルシステムのものだと確認した後にだけ使用してください。再フォーマットすると新しい UUID が作られ、ブロック単位の複製では同じ UUID が重複することがあります。一方、`PARTUUID=` はパーティションテーブルのエントリを識別するもので、意味が異なります。

:::single-choice{#fstab-uuid-source} ソースフィールドの `UUID=...` は、通常何を識別しますか？

::option[マウントポイントを所有するユーザーアカウント。]{#fstab-user-uuid explanation="アカウントの識別情報は、ファイルシステム UUID のソース構文では選択されません。"}
::option[その UUID を持つファイルシステムメタデータ。]{#fstab-filesystem-uuid .correct explanation="mount は、列挙名に依存せず、ファイルシステム識別子を利用可能なブロックデバイスへ解決します。"}
::option[最後にファイルシステムをアンマウントしたプロセス。]{#fstab-process-uuid explanation="プロセス履歴は、このソースフィールドに記録されません。"}
:::

## マウントオプションとチェック用フィールド

`defaults` は、実装で定義された一般的なオプションセットへ展開されます。すべてのマウントに最も安全な方針とは限りません。読み取り専用アクセス、デバイスノードや setuid 動作の制限など、信頼度とワークロードに応じたオプションを追加します。ネットワークやリムーバブルのファイルシステムでは、起動が予期せず停止しないように、タイムアウト、依存関係、障害許容の方針が必要になることがあります。

`fsck` に対応するファイルシステムでは、慣例としてルートファイルシステムに pass `1`、そのほかのチェック対象ローカルファイルシステムに pass `2` を使います。ただし、一般的な起動時 fsck を使わない種類があるなど、ファイルシステム固有の方法は異なります。機械的に `2` を割り当てず、インストール済みのファイルシステムとディストリビューションの文書に従ってください。

:::single-choice{#fstab-pass-zero} 6 番目のフィールドに `0` を指定すると、何が要求されますか？

::option[そのエントリを、fstab による自動 fsck の順序付けから除外する。]{#fstab-pass-zero-skip .correct explanation="pass が 0 のエントリは、このフィールドが管理する起動時チェックの順序から除外されます。"}
::option[どのような場合でもファイルシステムを読み取り専用でマウントする。]{#fstab-pass-zero-readonly explanation="読み取り専用の動作は、マウントオプションのフィールドで指定します。"}
::option[起動するたびにファイルシステムを消去する。]{#fstab-pass-zero-erase explanation="pass フィールドがファイルシステムをフォーマットまたは消去することはありません。"}
:::

## 復旧手段を用意して編集する

ルート、ブート、必須ネットワークのエントリが不正だと、起動が中断することがあります。編集前に次を行ってください。

1. 最新のバックアップと、コンソールまたはレスキュー環境へのアクセスを確認する。
2. パーミッションを保持したまま、既存ファイルをコピーする。
3. ソースの識別情報を確認し、目的のマウントポイントを作成する。
4. 範囲を限定した変更を 1 つ行う。
5. 再起動前に検証してテストする。

誰でも読める fstab エントリへ認証情報を直接書いてはいけません。該当するマウントヘルパーが提供する、保護された認証情報の仕組みを使用してください。

:::single-choice{#fstab-editing-recovery} 重要な fstab エントリを変更する前に、レスキューアクセスを確認するのはなぜですか？

::option[fstab を編集すると、必ずパーティションテーブルが即座に消去されるから。]{#fstab-no-partition-erase explanation="テキストの編集自体はディスクパーティションを書き換えません。ただし、その後のマウントが影響を及ぼすことはあります。"}
::option[このファイルは、別のオペレーティングシステムからしか編集できないから。]{#fstab-other-os-only explanation="適切な権限と安全策があれば、Linux 上で編集できます。"}
::option[不正なエントリにより、通常起動で使用可能な状態へ到達できなくなることがあるから。]{#fstab-boot-failure .correct explanation="重要なマウントの失敗は、緊急モードへの移行や依存サービスの停止を引き起こします。"}
:::

## 成功を思い込まずに検証する

対応している場合は、まず静的チェックを行います。

```bash
$ sudo findmnt --verify --verbose
```

続いて、制御された条件で新しいエントリだけをテストし、`findmnt` で確認します。一時的なテストならアンマウントしてください。`mount -a` は対象となる多数のエントリを実際に処理するため、ネットワークへ接続したり意図しないソースを接続したりすることがあります。また、マウント済みのエントリや `noauto` エントリを飛ばすため、無害な構文チェッカーでも完全な証明でもありません。

systemd ベースのシステムでは、fstab の編集後にマネージャーの設定を再読み込みし、生成されるマウントユニットを更新します。その後、ローカルの文書に従って依存関係と起動時の動作を確認してください。

:::single-choice{#fstab-mount-a-limit} `mount -a` だけでは fstab の完全な検証にならないのはなぜですか？

::option[一覧の全デバイスを、マウント前に必ず再フォーマットするから。]{#fstab-mount-a-formats explanation="通常、mount はファイルシステムを作成しません。"}
::option[一部のエントリを飛ばす一方、構文だけでなく広範な実マウント操作を行うから。]{#fstab-mount-a-incomplete .correct explanation="マウント済みまたは `noauto` のレコードはテストされない一方、対象となるソースには実際の影響が及びます。"}
::option[シェル履歴だけを読み、fstab を無視するから。]{#fstab-mount-a-history explanation="このコマンドは、対象となるエントリを fstab から読み取ります。"}
:::

ラボの復旧可能なセカンダリストレージで練習するには、[Linux パーティションとファイルシステムの管理](https://labex.io/ja/labs/comptia-manage-linux-partitions-and-filesystems-590845) を利用してください。

## まとめ

これで、永続的なファイルシステムテーブルのエントリを読み、検証できるようになりました。

1. ソース、対象、種類、オプション、dump、pass の各フィールドを読み取る。
2. 目的とする識別上の意味を持つ、確認済みの識別子を選ぶ。
3. 実際のファイルシステムに合わせて、マウントとチェックの方針を選ぶ。
4. レスキューアクセスを確保し、範囲を限定して 1 つずつ編集する。
5. 静的検証、対象を絞ったマウント、起動方針の確認を組み合わせる。
