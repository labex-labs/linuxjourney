`dd` は、指定されたブロックサイズと変換を適用しながら、入力ストリームから出力ストリームへデータをコピーします。ファイルシステム、パーティション境界、出力先に大切なデータがあるかどうかは理解しません。そのため、イメージや生デバイスの処理に役立つ一方、対象を誤れば直ちに破壊的な結果となります。

## 入力、出力、ブロックサイズ

コマンドの一般的な形は次のとおりです。

```bash
$ dd if=input.img of=output.img bs=4M status=progress
```

- `if=` は入力を選びます。省略すると、`dd` は標準入力から読み取ります。
- `of=` は出力を選びます。省略すると、`dd` は標準出力へ書き込みます。
- `bs=` は通常のコピーで入力と出力のブロックサイズを設定します。
- `status=progress` は GNU `dd` に転送の進捗を定期的に報告させます。

`dd` はブロックをコピーするのであり、本質的に1バイトずつコピーするわけではありません。大きな `bs` はシステムコールのオーバーヘッドを減らせる場合がありますが、最適な値はデバイス、アライメント、キャッシュ、ワークロードによって異なります。コピーされる論理データ自体は変わりません。

::option[`if=`]{#dd-command-input-file explanation="`if` は入力元を指定します。"}
::option[`of=`]{#dd-command-output-file .correct explanation="`of` はコピーされたデータを受け取る出力ストリームまたはファイルを指定します。"}
::option[`bs=`]{#dd-command-block-size explanation="`bs` はパスではなく転送ブロックサイズを選びます。"}
:::

## コピー量を制限する

`count=` は処理する入力ブロック数を制限します。通常の入力ファイルでは次のように使います。

```bash
$ dd if=source.img of=prefix.img bs=1M count=2 status=progress
```

これは最大1 MiBの入力ブロックを2個要求するため、最大2 MiBをコピーします。パイプのようなストリームでは短い読み取りにより単純な掛け算どおりにならない場合があります。完全な入力ブロックが必要なら、GNU `dd` には `iflag=fullblock` があります。2進単位と接尾辞の構文は、ローカル実装に従って区別してください。

:::single-choice{#dd-command-count-result} 通常ファイルに対する `bs=1M count=2` は、最大でどれだけのコピーを要求しますか？

::option[1 MiB。]{#dd-command-one-mib explanation="それは選択したサイズのブロック1個分です。"}
::option[2 MiB。]{#dd-command-two-mib .correct explanation="入力ブロック2個にブロックあたり1 MiBを掛けると、最大2 MiBになります。"}
::option[2 GiB。]{#dd-command-two-gib explanation="GNU `dd` の `M` 接尾辞は MiB サイズのブロックを表し、GiB ではありません。"}
:::

## イメージをブロックデバイスへ書き込む

生の復元は次のような形になります。

```bash
$ sudo dd if=backup.img of=/dev/sdX bs=4M status=progress conv=fsync
```

`/dev/sdX` は意図的に置かれたプレースホルダーであり、そのままコピーして実行するコマンドではありません。置き換える前に次を行います。

1. すべての大切なデータについて、復元テスト済みのバックアップを保持する。
2. `lsblk`、`udevadm` などでモデル、シリアル、サイズ、転送方式、永続リンクを確認し、対象を特定する。
3. 対象のパーティションがマウント済み、swap として使用中、RAID や LVM の一部、または別サービスからオープン中でないことを確認する。
4. 取り外し、再起動、トポロジー変更の後にはデバイスを再確認する。
5. イメージが収まることと、デバイス全体へ書き込む意図が本当にあることを確認する。

出力デバイスは先頭から上書きされます。`if` と `of` を逆にする、システムディスクを選ぶ、パーティションのつもりでディスク全体を指定するといった誤りは、確認プロンプトなしにデータを破壊します。

:::single-choice{#dd-command-target-verification} 生デバイスへ書き込む前に、モデル、シリアル、サイズ、使用状況を確認すべき最も強い理由はどれですか？

::option[デバイス文字は変わり得るうえ、`dd` は内容を理解せず、選択された対象を上書きするから。]{#dd-command-target-can-change .correct explanation="識別情報と使用状況の確認により、別のディスクや稼働中のストレージ層を破壊する危険を減らせます。"}
::option[ファイルシステムラベルがイメージと一致しなければ、`dd` が書き込みを拒否するから。]{#dd-command-label-check explanation="このツールは、そのようなファイルシステムを理解した安全確認を行いません。"}
::option[バックアップが一つでも存在すると、ブロックデバイスは開けないから。]{#dd-command-backup-prevents-open explanation="バックアップが技術的に書き込みを防ぐことはありません。維持され、テストされたバックアップは復旧手段を提供します。"}
:::

## 整合性のあるイメージを作成する

ファイルシステムが変化している最中に稼働中のブロックデバイスを読み取ると、内部的に整合しないイメージが作られる可能性があります。アンマウントしたファイルシステム、アプリケーション整合性のあるスナップショット、または文書化されたフリーズ／スナップショット手順を優先してください。データベースや仮想マシンでは、それぞれ固有の静止手順が必要な場合があります。

生デバイスイメージは、ファイルシステムのメタデータや未使用領域を含むブロックをコピーします。そのため、ファイル単位のバックアップよりはるかに大きくなる場合があり、複製を元のデバイスと同時にマウントする前に変更すべき識別子まで複製する可能性があります。

:::single-choice{#dd-command-live-filesystem-image} マウントされ、変化しているファイルシステムのイメージ作成が信頼できない場合があるのはなぜですか？

::option[マウント済みファイルシステムはブロックデバイスからの読み取りを一切許可しないから。]{#dd-command-mounted-no-read explanation="生の読み取りが可能な場合があるからこそ、整合性は仮定せず計画する必要があります。"}
::option[ファイルシステムの異なる時点から別々のブロックを読み取る可能性があるから。]{#dd-command-inconsistent-moments .correct explanation="並行して変更されると、収集したブロックイメージが一つの整合した時点を表さなくなる可能性があります。"}
::option[`dd` がファイルシステムを自動的に tar アーカイブへ変換するから。]{#dd-command-converts-tar explanation="このツールは生データをコピーし、ファイルシステムを理解したアーカイブは作りません。"}
:::

## 完了と検証

I/O エラーなしでコマンドが完了しても、意図した入力元と出力先を選んだことや、イメージが利用可能であることは証明できません。正確な識別情報とサイズを記録し、バッファー済み出力がストレージへ到達したことを確認し、適切に範囲を限定した読み戻しまたは暗号学的ハッシュを比較し、バックアップ計画に従って復旧をテストしてください。

SSD、フラッシュ変換層、シンプロビジョニングされたストレージ、スナップショット、再配置済みセクターに対して、`dd` の上書きを確実な安全消去として宣伝してはいけません。デバイスとプラットフォームが対応するサニタイズ機能を、明示的なデータ破棄ポリシーとともに使ってください。

:::single-choice{#dd-command-success-meaning} `dd` の終了ステータスが0でも、それだけでは何を証明できませんか？

::option[コマンドが指定された全オペランドを解析したこと。]{#dd-command-parsed-operands explanation="無効なオペランドは通常、正常完了ではなくエラーを引き起こします。"}
::option[操作した人が意図した入力元と出力先を選んだこと。]{#dd-command-does-not-prove-intent .correct explanation="ツールは操作意図を推測できないため、誤った対象へのコピーにも正常に成功できます。"}
::option[プロセスが通常の終了経路へ到達したこと。]{#dd-command-normal-exit explanation="ステータス0はコマンドレベルでの正常終了を示しますが、選択対象の意味的な正しさまでは示しません。"}
:::

生のハードウェアを扱う前に、通常ファイルまたは破棄可能な仮想ディスクだけで練習してください。[Linux のパーティションとファイルシステムを管理する](https://labex.io/labs/comptia-manage-linux-partitions-and-filesystems-590845)のパーティションとファイルシステムの概念が、重要な背景知識になります。

## まとめ

`dd` を、操作意図を理解しない生のブロックコピーツールとして捉えられるようになりました。

1. `if`、`of`、`bs`、`count` を区別する。
2. 永続的な対象識別情報と、稼働中のすべての利用元を確認する。
3. 整合したストレージ状態からイメージを作成する。
4. コピー後にフラッシュ、検証、復旧テストを行う。
5. 生デバイスへの出力はすべて破壊的になり得ると考える。
