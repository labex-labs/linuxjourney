ネットワークアドレス変換（NAT）は、パケットが変換装置を通過するときにアドレスフィールドを書き換え、多くの場合はトランスポート層のポートも書き換えます。プライベート IPv4 アドレスを持つネットワークを、より少数の外部ルーティング可能アドレスを介して接続するために広く使われています。

## 送信元の変換

送信元 NAT は、パケットがネットワークから出るときに送信元アドレスを置き換えます。多対一の構成では、複数の内部フローが一つの外部アドレスを共有できるように、送信元ポートも変換します。このポートを考慮した方式は NAPT や PAT、外部アドレスが変化し得る場合はマスカレードとも呼ばれます。

変換装置は対応関係を追跡し、応答パケットを元の内部エンドポイント宛てに書き戻せるようにします。通常は同じトランスポートフローを転送するので、アプリケーションプロキシのように別のプロキシ接続を開く必要はありません。

:::single-choice{#nat-source-translation} 送信元 NAT は外向きパケットの何を変更しますか？

::option[宛先アプリケーションのファイル権限だけ。]{#nat-file-permissions explanation="NAT が扱うのはネットワーク層とトランスポート層のヘッダーであり、リモートファイルシステムではありません。"}
::option[送信元アドレスと、多対一の利用では多くの場合は送信元ポート。]{#nat-source-fields .correct explanation="この対応付けにより、戻りのトラフィックを元の内部フローと関連付けられます。"}
::option[クライアントに恒久的に保存された DNS 名。]{#nat-dns-name explanation="変換によってクライアントの名前サービスデータベースが書き換えられることはありません。"}
:::

## 宛先の変換

宛先 NAT は宛先アドレスまたはポートを書き換えます。一般には、外部エンドポイントを通じて内部サービスを公開するために使われます。ポート転送ルールでは、外部の TCP ポートを別の内部アドレスとポートに対応付けることがあります。戻りのトラフィックには、対応する一貫した逆変換が必要です。

:::single-choice{#nat-port-forward} 受信ポート転送を実装する際に一般的に使われる NAT の形式はどれですか？

::option[経路検索前の送信元 NAT だけ。]{#nat-snat-port-forward explanation="内部の宛先を公開するには、宛先フィールドを変換する必要があります。"}
::option[アドレスもポートも一切変換しない。]{#nat-no-translation explanation="ポート転送ルールは、定義上、変換ポリシーです。"}
::option[宛先 NAT。]{#nat-dnat .correct explanation="DNAT は外部の宛先を、選択された内部サービスのエンドポイントに対応付けます。"}
:::

## NAT とファイアウォールポリシー

NAT はファイアウォールではありません。ステートフルな変換装置には、要求されていない受信トラフィックに対応するマッピングがない場合があります。しかし、何に到達できるかを決めるのは、明示的な転送、宛先変換、フィルタリング、アプリケーションの公開です。セキュリティポリシーはアドレスの書き換えから推測するのではなく、ファイアウォールルール、最小権限のサービス、エンドツーエンドの制御によって明示し、監査してください。

:::single-choice{#nat-not-firewall} NAT だけをセキュリティポリシーとして扱うべきでないのはなぜですか？

::option[NAT がすべてのペイロードを自動的に暗号化するから。]{#nat-encrypts explanation="アドレス変換はペイロードの機密性を提供しません。"}
::option[変換ルールとトラフィックのフィルタリングルールは目的が異なるから。]{#nat-filter-separate .correct explanation="変換があっても、到達性と認可には明示的なフィルタリングとサービスのポリシーが必要です。"}
::option[NAT によって管理者がファイアウォールルールを定義できなくなるから。]{#nat-prevents-firewall explanation="変換とファイアウォールポリシーは一般に併用されます。"}
:::

## 運用上の影響

NAT ではアドレスとポートの対応付けが枯渇することがあります。また、ピアツーピアプロトコルを複雑にし、アプリケーションから元の送信元を見えにくくし、アドレスを内部に埋め込むプロトコルに特別な処理を必要とする場合があります。フローを追跡する必要があるなら、ログには変換時刻とマッピングの詳細を残さなければなりません。

Linux では、現在のポリシーは一般に nftables とコネクショントラッキングで設定します。変更前に実際のルールセットを確認してください。

```bash
$ sudo nft list ruleset
$ sudo conntrack -L
```

2番目のコマンドには conntrack ツールと権限が必要です。ルールセットの変更でリモートアクセスが切断される可能性があるため、コンソールからの復旧手段、アトミックな設定、検証、切り戻しを用意してください。

:::single-choice{#nat-trace-flow} 共有アドレスを使うフローを内部クライアントまで追跡するには、どの証拠が必要ですか？

::option[時刻やポートを伴わない外部アドレスだけ。]{#nat-address-only explanation="多数のクライアントとフローがそのアドレスを共有できます。"}
::option[クライアントに表示されたホスト名だけ。]{#nat-hostname-only explanation="変換装置が対応付けるのはパケットのタプルであり、必ずしもホスト名ではありません。"}
::option[プロトコルとポートを含み、時刻で対応付けられた変換マッピング。]{#nat-correlated-mapping .correct explanation="完全なタプルとタイムスタンプが、同時に存在する変換済みフローを区別します。"}
:::

## まとめ

アドレス変換を、ルーティング、プロキシ、ファイアウォールポリシーから区別できるようになりました。

1. 外向きフローの送信元変換を識別する。
2. 公開サービスでの宛先変換を識別する。
3. ポートの対応付けによってアドレスを共有できる仕組みを理解する。
4. NAT をセキュリティと見なさず、明示的なフィルタリングを適用する。
5. 変更時にはマッピングの証拠と復旧用アクセスを確保する。
