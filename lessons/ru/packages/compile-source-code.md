Сборка из исходного кода может предоставить версию или функцию, отсутствующую в настроенных репозиториях, но переносит работу по интеграции, обновлению и доверию с дистрибутива на вас. Если поддерживаемый пакет дистрибутива решает задачу, предпочитайте его.

## Проверка и чтение до сборки

Получите исходный код из аутентифицированного канала выпусков исходного проекта. Проверьте его подпись или контрольную сумму через доверенный путь, затем исследуйте архив до извлечения в непривилегированный промежуточный каталог. Прочитайте файлы `README`, `INSTALL`, `SECURITY` и документацию проекта по сборке.

Инструкции сборки являются исполняемым кодом. Скрипт `configure`, определение сборки, тест или плагин компилятора способны запускать произвольные команды от имени вашего пользователя. Не собирайте недоверенный исходный код и не запускайте саму сборку через `sudo`.

:::single-choice{#compile-source-code-build-privilege} Почему этап компиляции обычно следует выполнять без `sudo`?

::option[Компиляторы отказываются создавать машинный код для пользователя root.]{#compile-source-code-root-compiler explanation="Компиляторы могут работать от root, но это без необходимости увеличивает риск."}
::option[`sudo` автоматически удаляет каждый созданный объектный файл.]{#compile-source-code-sudo-delete explanation="Повышение привилегий само по себе не удаляет результаты сборки."}
::option[Логика сборки может выполнять произвольные команды и обычно не требует системных привилегий.]{#compile-source-code-unprivileged-build .correct explanation="Непривилегированная сборка ограничивает ущерб от ошибок или вредоносных инструкций."}
:::

## Установка требований сборки

В системе разработки семейства Debian распространённой отправной точкой служит:

```bash
$ sudo apt install build-essential
```

Команда устанавливает базовый компилятор и инструменты сборки, но не все зависимости любого проекта. Проектам также могут понадобиться среды выполнения языков, генераторы, инструменты систем сборки, заголовки разработки или точные версии библиотек. Устанавливайте требования из доверенных репозиториев и отличайте зависимости сборки от зависимостей времени выполнения.

:::single-choice{#compile-source-code-build-essential-scope} Что предоставляет `build-essential` в системе семейства Debian?

::option[Базовый набор распространённых инструментов компиляции и сборки.]{#compile-source-code-baseline-tools .correct explanation="Он предоставляет основные инструменты, но не может предусмотреть все библиотеки и генераторы конкретных проектов."}
::option[Все зависимости каждого проекта исходного кода.]{#compile-source-code-all-dependencies explanation="Отдельные проекты объявляют дополнительные, иногда привязанные к версиям требования."}

## Настройка и сборка

Традиционный проект в стиле Autoconf использует:

```bash
$ ./configure --prefix=/usr/local
$ make
```

`configure` проверяет среду и создаёт файлы сборки согласно выбранным параметрам. `make` читает правила зависимостей и команд, обычно из `Makefile`, и создаёт запрошенные цели.

Эта последовательность не универсальна. Проекты могут использовать CMake, Meson, Ninja, инструменты конкретного языка или собственные скрипты. Следуйте документации точного выпуска, а не запускайте `./configure` лишь по привычке. Если система сборки поддерживает это, отдельный каталог сборки помогает отделить созданные файлы.

:::single-choice{#compile-source-code-make-role} Что делает `make` в традиционном процессе?

::option[Регистрирует каждый результат в базе пакетов дистрибутива.]{#compile-source-code-make-package-db explanation="Одна лишь компиляция не создаёт записи владения собственных пакетов."}
::option[Автоматически загружает аутентифицированный выпуск исходного кода.]{#compile-source-code-make-download explanation="Получение и проверка исходного кода происходят до локальной сборки, если проект явно не определяет иначе."}
::option[Выполняет применимые правила из описания сборки.]{#compile-source-code-make-rules .correct explanation="Make оценивает зависимости и запускает команды, необходимые для актуализации выбранных целей."}
:::

## Тестирование до установки

Запустите документированную тестовую цель проекта, например:

```bash
$ make check
```

Настоящая цель может называться `test`, `check` или быть отдельной командой. Исследуйте сбои, а не устанавливайте непроверенный результат. Тестам могут потребоваться сеть, службы, специальное оборудование или изоляция; проверяйте их до выполнения так же, как другой код сборки.

:::single-choice{#compile-source-code-test-failure} Что делать, если документированный набор тестов завершается с ошибкой?

::option[Немедленно запустить ту же установку от root.]{#compile-source-code-install-after-failure explanation="Привилегии не устраняют неизвестную ошибку корректности и увеличивают последствия."}
::option[Удалить базу диспетчера пакетов во избежание конфликтов.]{#compile-source-code-delete-database explanation="Собственная база не связана с устранением ошибки тестов исходного кода и не должна удаляться."}
::option[Исследовать сбой до установки сборки.]{#compile-source-code-investigate-tests .correct explanation="Неудачный тест может выявить несовместимые зависимости, дефекты сборки или предположения о среде."}
:::

## Промежуточное размещение и отслеживание установки

`sudo make install` может напрямую скопировать файлы в системные префиксы, не записав их в собственную базу пакетов. Цели удаления необязательны и могут быть неполными, а последующие обновления способны перезаписать или оставить файлы без владельца.

Предпочитайте один из контролируемых подходов:

- создайте официальный собственный пакет инструментами дистрибутива
- устанавливайте в явно отделённый префикс, например `/usr/local`, если это разрешает политика
- разместите файлы в промежуточном корне упаковки через поддерживаемый механизм вроде `DESTDIR`
- используйте непривилегированный пользовательский префикс, изолированное окружение или контейнер, когда это уместно

`checkinstall` может создать простой пакет для некоторых процессов `make install`, но он не универсален и не заменяет проверенный рецепт пакета качества дистрибутива. Никогда не считайте его обязательным правилом. До любого привилегированного копирования проверьте промежуточный список файлов, владельцев, права, пути и план удаления или обновления.

:::single-choice{#compile-source-code-destdir-purpose} Каково назначение поддерживаемой промежуточной установки через `DESTDIR`?

::option[Поместить предназначенные для установки файлы под временный корень для проверки или упаковки.]{#compile-source-code-stage-root .correct explanation="Промежуточное размещение отделяет сбор файлов от немедленной записи в действующий системный префикс."}
::option[Преобразовать компилятор в удалённый репозиторий пакетов.]{#compile-source-code-destdir-repository explanation="Переменная перенаправляет пути установки и не публикует метаданные репозитория."}
::option[Пропустить компиляцию и вместо неё загрузить неизвестные двоичные файлы.]{#compile-source-code-destdir-download explanation="Промежуточное размещение применяется после сборки и не заменяет её внешней двоичной загрузкой."}
:::

Используйте лабораторию [Сборка программного обеспечения из исходного кода в Linux](https://labex.io/ru/labs/comptia-build-software-from-source-code-in-linux-590853) в одноразовой среде, чтобы отработать процесс, не смешивая экспериментальные файлы с производственной системой.

## Итоги

Теперь вы можете рассматривать сборку из исходного кода как контролируемый процесс поставки программ.

1. Аутентифицируйте исходный код и проверяйте его инструкции как исполняемый код.
2. Устанавливайте явные требования сборки из доверенных репозиториев.
3. Настраивайте, собирайте и тестируйте без ненужных привилегий.
4. Размещайте и проверяйте результат до системной установки.
5. Отслеживайте установленные файлы собственным пакетом или намеренно изолированным префиксом.
