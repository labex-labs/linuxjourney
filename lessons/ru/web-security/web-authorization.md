Даже после входа у пользователя может не быть права на конкретное действие. **Авторизация** решает, может ли указанная учётная запись выполнить действие с данным ресурсом.

## Как читать правила доступа

**Роль** — это именованный набор прав. Эти учебные правила относятся к сервису предварительного просмотра.

```text
Role       View published page   Edit draft
Reader    Yes                   No
Editor    Yes                   Yes
```

Найдите строку с ролью пользователя и столбец с нужной операцией. Редактор может просматривать опубликованную страницу и править черновик. Читатель может просматривать опубликованную страницу.

:::single-choice{#web-authorization-read-policy} Вошедший читатель просит отредактировать черновик. Что показывает таблица?

::option[Для роли Reader действие запрещено.]{#web-authorization-read-policy-b .correct explanation="В строке Reader в столбце Edit draft указано No."}
::option[Действие разрешено любой вошедшей учётной записи.]{#web-authorization-read-policy-a explanation="Право на это действие зависит от роли."}
::option[Чтобы получить право редактирования, нужно перейти на HTTPS.]{#web-authorization-read-policy-c explanation="Защита соединения не назначает права внутри приложения."}
:::

## Как проверить нужный ресурс

Многие системы назначают разные права для разных ресурсов. Например, редактор может менять черновики в своём проекте и только просматривать страницы другого проекта. В проверке укажите и операцию, и целевой ресурс.

:::single-choice{#web-authorization-target-resource} Майя может редактировать проект A. Что определяет, может ли она редактировать проект B?

::option[Название проекта A.]{#web-authorization-target-resource-b explanation="Название ничего не говорит о доступе к другому проекту."}
::option[Успешный вход Майи.]{#web-authorization-target-resource-c explanation="Аутентификация устанавливает учётную запись Майи. Право на ресурс проверяется отдельно."}
::option[Правила доступа для Майи к проекту B.]{#web-authorization-target-resource-a .correct explanation="Прежнее разрешение относилось к конкретному ресурсу."}
:::

## Где проверять права

Интерфейс может скрывать элементы редактирования от читателей. Сервер всё равно должен проверять права при каждом запросе. Для учебного сервиса проверьте ожидаемое разрешение и ожидаемый отказ обычными согласованными действиями.

:::single-choice{#web-authorization-decision-location} Приложение скрывает кнопку Edit от читателей. Где ещё должны применяться правила доступа?

::option[Только в браузере, когда он выбирает, какую кнопку показать.]{#web-authorization-decision-location-a explanation="Браузер управляет интерфейсом. Решение о доступе по поступившему запросу принимает сервис."}
::option[В сервисе, который получает запрос на операцию.]{#web-authorization-decision-location-c .correct explanation="Сервис может каждый раз проверять учётную запись, действие и целевой ресурс."}
::option[Только на странице со списком ролей.]{#web-authorization-decision-location-b explanation="Показ имени роли не ограничивает выполнение операции."}
:::

## Итоги

Теперь вы можете объяснить, как приложение принимает решение о доступе.

1. Сопоставить роль учётной записи с запрошенным действием.
2. Учитывать конкретный ресурс при проверке.
3. Убедиться, что сервис применяет правила к запросам.
