HTTP определяет сообщения, которыми обмениваются браузер и сервер. HTTPS передаёт те же сообщения через **TLS** — протокол, который защищает соединение и помогает браузеру проверить подлинность сервера.

## Как определить защищённое соединение

Представьте, что браузер подключается к `https://site.example`. После установки соединения TLS браузер и сервер могут обмениваться зашифрованными сообщениями HTTP. Наблюдатель на этом участке сети не может просто прочитать тело сообщения HTTP или незаметно изменить его.

```text
Browser  ===== HTTPS connection =====  Website server
```

Браузеру всё равно нужно проверить подлинность сервера, с которым он устанавливает соединение.

:::single-choice{#web-https-protected-hop} Что защищает HTTPS в этом простом примере?

::option[Страницу, которую браузер уже отобразил.]{#web-https-protected-hop-b explanation="Браузер читает страницу после расшифровки ответа."}
::option[Все резервные копии сайта.]{#web-https-protected-hop-c explanation="Защита резервных копий решается отдельно."}
::option[Сообщения HTTP, передаваемые по защищённому соединению.]{#web-https-protected-hop-a .correct explanation="TLS защищает сообщения при передаче между двумя сторонами соединения."}
:::

## Как читать путь с несколькими участками

Прокси может принять запрос браузера и переслать его другому серверу. Если соединение TLS завершается на прокси, тот может прочитать запрос перед пересылкой. Следующее соединение нуждается в собственной защите. Проверяйте каждый участок отдельно.

```text
Browser  === HTTPS ===  Proxy  --- HTTP ---  Internal server
```

На схеме внешнее соединение использует TLS. Внутреннее работает по обычному HTTP.

:::single-choice{#web-https-inner-hop} Какой участок требует отдельного изменения, чтобы получить защиту TLS?

::option[От браузера до прокси.]{#web-https-inner-hop-a explanation="На этом участке уже используется HTTPS."}
::option[От прокси до внутреннего сервера.]{#web-https-inner-hop-b .correct explanation="Внутренний участок на схеме использует обычный HTTP."}
::option[Вкладка браузера, которая вообще не запрашивает сайт.]{#web-https-inner-hop-c explanation="У этой вкладки нет соединения на схеме."}
:::

## Отдельная проверка прав доступа

Проверенное защищённое соединение помогает подтвердить подлинность сервера и защищает сообщения при передаче. Приложение по-прежнему решает, какой учётной записи разрешено читать страницу или менять настройку. Даже при надёжном TLS для закрытой страницы нужны свои правила доступа.

:::single-choice{#web-https-access-vs-transport} Что должен проверить сервис, прежде чем вернуть закрытую страницу учётной записи?

::option[Может ли прошедшая аутентификацию учётная запись читать эту страницу.]{#web-https-access-vs-transport-c .correct explanation="Авторизация в приложении определяет, к чему имеет доступ учётная запись."}
::option[Только то, используется ли TLS.]{#web-https-access-vs-transport-a explanation="HTTPS защищает обмен. Сервис по-прежнему должен проверить права доступа."}
::option[Только то, охватывает ли сертификат запрошенное имя хоста.]{#web-https-access-vs-transport-b explanation="Сертификат помогает проверить подлинность сервера. Доступ к закрытым страницам определяет приложение."}
:::

## Итоги

Теперь вы можете объяснить, что HTTPS защищает на пути веб-запроса.

1. Определить, где TLS начинается и заканчивается.
2. Проверить каждый участок, если прокси пересылает запрос.
3. Объяснить, зачем приложению нужны собственные правила доступа.
