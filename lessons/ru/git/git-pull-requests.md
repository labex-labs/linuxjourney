**Пул-реквест** (pull request, или PR) — это предложение перенести изменения из одной ветки в другую. Git ведёт учёт коммитов и веток. На платформе размещения репозитория эти изменения можно изучить и обсудить на странице проверки кода, где также показываются результаты проверок.

## Находим исходную и целевую ветки

Коллега предлагает добавить на сайт страницу состояния. На странице проверки кода указано `health-page → main`. Исходная ветка, которую иногда называют **head**, содержит предлагаемые изменения. Целевая ветка, она же **base**, должна их получить.

```text
Source: health-page at 3ab4501
Target: main
Changed file: health.txt
```

Пока на странице проверки кода видно только предложение. Изменения попадут в целевую ветку, когда PR будет слит.

:::single-choice{#git-pull-requests-pr-direction} Какая ветка получит страницу состояния при слиянии этого PR?

::option[Ветка с именем, совпадающим с идентификатором коммита.]{#git-pull-requests-pr-direction-a explanation="Это значение обозначает снимок. Целевая ветка определяется по её имени."}
::option[Ветка main.]{#git-pull-requests-pr-direction-b .correct explanation="Целевая ветка — main, поэтому изменение попадёт в неё."}
::option[Ветка health-page.]{#git-pull-requests-pr-direction-c explanation="Изменение поступит из исходной ветки health-page."}
:::

## Смотрим различия между версиями

Откройте список изменённых файлов и прочитайте, чем предлагаемая версия отличается от целевой ветки PR. Одна добавленная строка в `health.txt` подходит для небольшой страницы состояния. Если среди изменений вы видите ещё и правку `index.html`, проверьте, относится ли она к тому же предложению. Ориентируйтесь на файлы, которые действительно указаны в PR.

:::single-choice{#git-pull-requests-unexpected-file} PR с заголовком «Добавить страницу состояния» меняет и главную страницу. Где посмотреть точную правку?

::option[В списке изменённых файлов, в сравнении версий.]{#git-pull-requests-unexpected-file-a .correct explanation="Сравнение показывает, какие строки меняются в этом предложении."}
::option[Только в заголовке PR.]{#git-pull-requests-unexpected-file-b explanation="Заголовок передаёт основную идею и может опускать детали."}
::option[В имени ветки.]{#git-pull-requests-unexpected-file-c explanation="Имя ветки обозначает направление работы и не описывает отдельные правки."}
:::

## Читаем результаты автоматических проверок

Сервис размещения репозитория может запускать тест при изменении PR. Посмотрите, к какому коммиту или версии относится результат. Если после успешного запуска добавили ещё один коммит, убедитесь, что для новой версии выполнили необходимые проверки. Успешный результат относится только к тем проверкам, которые были запущены.

:::single-choice{#git-pull-requests-changed-revision} Тест прошёл для 3ab4501. Теперь PR указывает на 78ac900. Что стоит проверить, прежде чем полагаться на результат?

::option[Насколько понятно написано сообщение исходного коммита.]{#git-pull-requests-changed-revision-a explanation="Из сообщения нельзя узнать, проверялся ли новый коммит."}
::option[Остался ли прежним заголовок PR.]{#git-pull-requests-changed-revision-b explanation="Заголовок может не меняться, даже когда меняется код."}
::option[Были ли запущены проверки для новой версии.]{#git-pull-requests-changed-revision-c .correct explanation="Предыдущий результат относится к другой версии."}
:::

## Итоги

Теперь вы можете понять, что предлагается в пул-реквесте, и проверить, на чём основано решение о слиянии.

1. Найдите исходную и целевую ветки.
2. Проверьте предлагаемые правки в списке изменённых файлов.
3. Уточните, к какой версии относится результат автоматической проверки.
