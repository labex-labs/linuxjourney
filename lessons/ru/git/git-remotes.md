**Удалённый репозиторий** в настройках Git — именованный адрес, по которому локальный репозиторий может обратиться к другому. Тот может находиться на сервисе размещения репозиториев или в каталоге на том же компьютере. В упражнении используется отдельный локальный каталог, поэтому учётная запись на внешнем сервисе не нужна.

## Добавляем адрес

Из учебного репозитория создайте отдельный **пустой репозиторий без рабочего дерева** (bare). В нём хранятся история и ссылки Git, а рабочих файлов проекта в нём нет. Он может принимать коммиты из вашего рабочего репозитория. Чтобы начать упражнение заново, нужен ещё не использованный каталог `journey-remote.git`.

```bash
$ git init --bare --initial-branch=main ../journey-remote.git
$ git remote add origin ../journey-remote.git
$ git remote -v
```

Удалённому репозиторию часто дают имя `origin`. В списке подключённых репозиториев видно, какому адресу соответствует это имя.

:::single-choice{#git-remotes-add-address} Вы выполнили git remote add и увидели в списке origin. Что сделал Git?

::option[Сохранил имя для адреса другого репозитория.]{#git-remotes-add-address-b .correct explanation="В следующих командах вы можете указывать этот адрес как origin."}
::option[Отправил все локальные коммиты.]{#git-remotes-add-address-a explanation="Добавление репозитория сохраняет его адрес. Для отправки используется push."}
::option[Клонировал ещё одно рабочее дерево внутрь проекта.]{#git-remotes-add-address-c explanation="Существующее рабочее дерево остаётся на прежнем месте."}
:::

## Отправляем ветку

Используйте `git push`, чтобы отправить локальные коммиты и попросить другой репозиторий обновить ветку. Параметр `-u` записывает удалённую ветку как вышестоящую (upstream). Git будет связывать её с локальной веткой в последующих командах.

```bash
$ git push -u origin main
```

В этом упражнении данные отправляются только в отдельный учебный каталог. Общий репозиторий может требовать соответствующих прав и отклонять обновления. Проверяйте ответ, чтобы убедиться, что отправка прошла успешно.

:::single-choice{#git-remotes-push-direction} Какой командой можно отправить новый коммит локальной ветки main в этот удалённый репозиторий?

::option[git fetch origin]{#git-remotes-push-direction-b explanation="Fetch получает данные из удалённого репозитория в локальный."}
::option[git remote -v]{#git-remotes-push-direction-c explanation="Команда показывает, какой адрес соответствует имени origin."}
::option[git push origin main]{#git-remotes-push-direction-a .correct explanation="Push отправляет коммиты, которых не хватает удалённому репозиторию, и запрашивает обновление ветки."}
:::

## Получаем обновление

Используйте `git fetch origin`, чтобы обновить сведения об удалённой истории. Git запоминает последнее полученное состояние в **ветке слежения за удалённой веткой**, например `origin/main`. Посмотреть её историю можно командой `git log --oneline origin/main`. Сам по себе fetch оставляет рабочее дерево на текущей локальной ветке.

```bash
$ git fetch origin
$ git log --oneline origin/main
```

:::single-choice{#git-remotes-after-fetch} После fetch ветка origin/main продвинулась, а локальная main осталась на прежнем месте. Что произошло?

::option[Fetch перезаписал файлы, которые вы редактировали.]{#git-remotes-after-fetch-a explanation="Fetch обновляет сохранённые сведения об удалённой ветке."}
::option[Git получил сведения об удалённом изменении. Объединение с локальной веткой — отдельный шаг.]{#git-remotes-after-fetch-c .correct explanation="Локальная ветка может остаться на месте, пока origin/main продвигается."}
::option[В ходе fetch ваша команда push обновила удалённый репозиторий.]{#git-remotes-after-fetch-b explanation="Fetch получает данные из удалённого репозитория."}
:::

## Итоги

Теперь вы можете определить, в каком репозитории происходят изменения при выполнении команды Git.

1. Добавьте удалённый адрес и проверьте его.
2. Отправьте ветку и определите её вышестоящую ветку.
3. Получите обновлённую удалённую историю, сохранив открытые рабочие файлы без изменений.
