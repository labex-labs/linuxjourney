Преобразование сетевых адресов изменяет поля адресов, а часто и транспортные порты, когда пакеты проходят через выполняющее преобразование устройство. NAT широко применяется, чтобы подключать сети IPv4 с частной адресацией через меньший набор внешних маршрутизируемых адресов.

## Преобразование источника

Source NAT заменяет адрес источника исходящего из сети пакета. В схемах «многие к одному» также преобразуются порты источника, чтобы несколько внутренних потоков могли совместно использовать один внешний адрес. Такая учитывающая порты форма часто называется NAPT, PAT или маскарадингом, если внешний адрес способен изменяться.

Преобразователь отслеживает сопоставления, чтобы ответные пакеты можно было переписать обратно для исходной внутренней конечной точки. Обычно он пересылает тот же транспортный поток и не обязан открывать отдельное прокси-соединение, как это делал бы прокси уровня приложений.

:::single-choice{#nat-source-translation} Что source NAT изменяет в исходящем пакете?

::option[Только права доступа к файлам приложения назначения.]{#nat-file-permissions explanation="NAT работает с сетевыми и транспортными заголовками, а не с удалёнными файловыми системами."}
::option[Адрес источника, а при схеме «многие к одному» часто и порт источника.]{#nat-source-fields .correct explanation="Сопоставление позволяет связать ответный трафик с исходным внутренним потоком."}
::option[DNS-имя, навсегда сохранённое клиентом.]{#nat-dns-name explanation="Преобразование не переписывает базу службы имён клиента."}
:::

## Преобразование назначения

Destination NAT переписывает адрес или порт назначения — обычно для публикации внутренней службы через внешнюю конечную точку. Правило перенаправления порта может сопоставить внешний порт TCP с другим внутренним адресом и портом. Для обратного трафика требуется согласованное обратное преобразование.

:::single-choice{#nat-port-forward} Какая форма NAT обычно реализует перенаправление входящего порта?

::option[Только source NAT перед поиском маршрута.]{#nat-snat-port-forward explanation="Для публикации внутреннего назначения нужно преобразовать поля назначения."}
::option[Полное отсутствие преобразования адресов и портов.]{#nat-no-translation explanation="Правило перенаправления порта по определению является политикой преобразования."}
::option[Destination NAT.]{#nat-dnat .correct explanation="DNAT сопоставляет внешнее назначение с выбранной конечной точкой внутренней службы."}
:::

## NAT и политика межсетевого экрана

NAT — не межсетевой экран. У преобразователя с отслеживанием состояния может не быть сопоставления для незапрошенного входящего трафика, но доступность определяют явная пересылка, преобразование назначения, фильтрация и публикация приложений. Политику безопасности следует задавать и проверять с помощью правил межсетевого экрана, служб с минимальными привилегиями и сквозных средств защиты, а не выводить из самого факта изменения адресов.

:::single-choice{#nat-not-firewall} Почему NAT сам по себе нельзя считать политикой безопасности?

::option[NAT автоматически шифрует каждую полезную нагрузку.]{#nat-encrypts explanation="Преобразование адресов не обеспечивает конфиденциальность полезной нагрузки."}
::option[У правил преобразования и правил фильтрации трафика разные задачи.]{#nat-filter-separate .correct explanation="Даже при наличии преобразования доступность и авторизация требуют явной фильтрации и политики служб."}
::option[NAT не позволяет администраторам определять правила межсетевого экрана.]{#nat-prevents-firewall explanation="Преобразование и политика межсетевого экрана обычно используются совместно."}
:::

## Эксплуатационные последствия

NAT может исчерпать сопоставления адресов и портов, усложнить одноранговые протоколы, скрыть от приложений исходные адреса и потребовать особой обработки протоколов, встраивающих адреса в данные. Если потоки необходимо отслеживать, журналы должны сохранять временные метки преобразований и сведения о сопоставлениях.

В Linux современные политики обычно настраиваются с помощью nftables и отслеживания соединений. Перед изменениями проверьте фактический набор правил:

```bash
$ sudo nft list ruleset
$ sudo conntrack -L
```

Для второй команды нужны инструменты conntrack и соответствующие привилегии. Изменение набора правил может оборвать удалённый доступ, поэтому предусмотрите восстановление через консоль, атомарное применение конфигурации, проверку и откат.

:::single-choice{#nat-trace-flow} Какие данные нужны, чтобы связать поток через общий адрес с внутренним клиентом?

::option[Только внешний адрес без времени и порта.]{#nat-address-only explanation="Один адрес может совместно использоваться множеством клиентов и потоков."}
::option[Только отображаемое имя узла клиента.]{#nat-hostname-only explanation="Преобразователь сопоставляет кортежи полей пакета, а не обязательно имена узлов."}
::option[Сопоставление преобразования с привязкой ко времени, включая протокол и порты.]{#nat-correlated-mapping .correct explanation="Полный кортеж и временная метка позволяют различить одновременные преобразованные потоки."}
:::

## Итоги

Теперь вы можете отличать преобразование адресов от маршрутизации, проксирования и политики межсетевого экрана.

1. Распознавайте преобразование источника в исходящих потоках.
2. Распознавайте преобразование назначения при публикации служб.
3. Понимайте, как сопоставления портов позволяют совместно использовать адрес.
4. Применяйте явную фильтрацию, а не считайте NAT средством безопасности.
5. При изменениях сохраняйте данные сопоставлений и доступ для восстановления.
