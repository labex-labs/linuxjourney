Сетевой интерфейс Linux соединяет сетевое пространство имён с физическим устройством, петлёй обратной связи, мостом, туннелем, виртуальным устройством или другим каналом. Состояние интерфейса, адреса, маршруты, DNS и постоянная конфигурация связаны, но представляют собой разные сущности.

## Обнаружение интерфейсов

Используйте современные инструменты iproute2:

```bash
$ ip -brief link show
$ ip -brief address show
```

Интерфейсы могут иметь предсказуемые имена на основе оборудования, например `enp1s0`, традиционные имена вроде `eth0` или имена, заданные администратором. Никогда не предполагайте, что `eth0` существует или обозначает конкретный адаптер.

:::single-choice{#interfaces-name-assumption}
Почему скрипту следует обнаруживать интерфейс, а не предполагать наличие `eth0`?

::option[Каждый интерфейс обязан называться `lo`.]{#interfaces-all-loopback explanation="Обратная петля — один особый интерфейс, а не имя любого канала."}
::option[В системах Linux применяются разные схемы именования интерфейсов.]{#interfaces-naming-varies .correct explanation="Имена на основе оборудования, виртуальные и пользовательские имена делают фиксированное предположение об eth0 ненадёжным."}
::option[Имена интерфейсов всегда являются удалёнными паролями.]{#interfaces-name-password explanation="Имена обозначают устройства ядра и не являются учётными данными."}
:::

## Административное и рабочее состояние

`UP` означает, что интерфейс административно включён. `LOWER_UP` обычно указывает на сообщаемую нижним уровнем готовность к работе, например наличие несущей Ethernet. Ни один из этих флагов сам по себе не доказывает работу IP-адреса, маршрута, DNS, межсетевого экрана или сквозного пути приложения.

```bash
$ ip -details link show dev enp1s0
$ ip -s link show dev enp1s0
```

Статистика может показать ошибки, отброшенные пакеты и счётчики, но для осмысленной интерпретации счётчикам нужны временной интервал и исходный уровень.

:::single-choice{#interfaces-up-limit}
Чего не доказывает административное состояние `UP`?

::option[Работоспособности сквозного соединения.]{#interfaces-up-not-connectivity .correct explanation="Могут сохраняться сбои нижнего уровня, адресации, маршрутизации, фильтрации, именования или службы."}
::option[Того, что администратор включил интерфейс.]{#interfaces-up-does-prove explanation="Именно это состояние непосредственно и означает."}
::option[Того, что у интерфейса есть объект ядра.]{#interfaces-up-kernel-object explanation="Отображаемое состояние принадлежит существующему интерфейсу ядра."}
:::

## Изменение текущего состояния

К командам изменения текущего состояния относятся:

```bash
$ sudo ip link set dev enp1s0 up
$ sudo ip address add 192.0.2.10/24 dev enp1s0
```

Эти изменения затрагивают текущее состояние ядра и могут конфликтовать с диспетчером сети, который позже повторно применит свой профиль. Отключение интерфейса удалённого управления способно немедленно прервать доступ. Перед изменением проверьте точное устройство, обеспечьте доступ через консоль, запишите текущее состояние и подготовьте проверенный или запускаемый по таймеру откат.

:::single-choice{#interfaces-ip-address-add-persistence}
Гарантирует ли сама по себе команда `ip address add` сохранение настройки после перезагрузки?

::option[Нет; активная система настройки должна также сохранить этот параметр.]{#interfaces-manager-persistence .correct explanation="Постоянную политику применяет NetworkManager, systemd-networkd, ifupdown или другой владелец конфигурации."}
::option[Да, поскольку любое изменение ядра редактирует профили всех диспетчеров.]{#interfaces-runtime-always-persistent explanation="Изменения текущего состояния ядра не обновляют автоматически любую постоянную конфигурацию."}
::option[Только если это частный адрес IPv4.]{#interfaces-private-persistent explanation="Область действия адреса не делает команду текущего состояния постоянной."}
:::

## Определение владельца конфигурации

Пути постоянной конфигурации различаются между дистрибутивами и установками. Возможны профили NetworkManager, модули systemd-networkd, исходные файлы netplan, `/etc/network/interfaces`, cloud-init или системы оркестрации. Прежде чем редактировать файлы, определите, какая служба управляет устройством:

```bash
$ systemctl --type=service --state=running | grep -E 'NetworkManager|networkd|networking'
$ networkctl status
$ nmcli device status
```

Используйте только те команды, которые доступны для обнаруженного диспетчера. Если одной связью управляют два диспетчера, они могут конкурировать и перезаписывать состояние друг друга.

:::single-choice{#interfaces-config-owner}
Что следует сделать перед постоянным изменением интерфейса?

::option[Отредактировать все возможные файлы настройки сети.]{#interfaces-edit-all explanation="Конкурирующие определения создают конфликты и непредсказуемое повторное применение."}
::option[Определить, какой диспетчер сети управляет интерфейсом.]{#interfaces-identify-owner .correct explanation="Правильный источник конфигурации и способ применения зависят от владельца."}
::option[Удалить все текущие маршруты до их проверки.]{#interfaces-delete-routes explanation="Это разрушительное действие, способное лишить вас пути восстановления."}
:::

## Проверка изменения

Проверьте состояние канала, назначенные адреса и сроки их действия, выбранные маршруты, состояние механизма разрешения имён, доступность соседей и само приложение. Для постоянного изменения проверяйте управляемый перезапуск службы или перезагрузку только при наличии пути восстановления.

:::single-choice{#interfaces-change-verification}
Что служит более веским доказательством, чем появление нового адреса в выводе `ip address`?

::option[В имени интерфейса есть цифра.]{#interfaces-digit explanation="Именование ничего не подтверждает о сквозной работе."}
::option[Цвет приглашения оболочки не изменился.]{#interfaces-prompt-color explanation="Внешний вид терминала не связан с работой сети."}
::option[Маршруты, разрешение имён и требуемое приложение также работают.]{#interfaces-end-to-end .correct explanation="Рабочая конфигурация зависит от полного пути и поведения службы."}
:::

## Итоги

Теперь вы умеете проверять и изменять интерфейс, не смешивая текущее состояние с постоянной политикой.

1. Обнаруживайте настоящие имена и адреса интерфейсов.
2. Отличайте административное состояние от рабочей связности.
3. Рассматривайте прямые изменения через `ip` как текущее состояние ядра.
4. Перед постоянными изменениями определяйте активного владельца конфигурации.
5. После изменений проверяйте маршрутизацию, разрешение имён и работу приложения.
