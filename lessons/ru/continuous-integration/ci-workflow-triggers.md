Рабочий процесс запускается в ответ на определённое событие. В GitHub Actions такие события перечислены в разделе `on`. **Событием** может быть отправка коммита в ветку, изменение пул-реквеста или другое поддерживаемое действие.

## Разбираем триггер отправки

Прочитайте этот фрагмент рабочего процесса. В YAML отступы показывают, что `branches` — настройка события `push`.

```yaml
on:
  push:
    branches:
      - main
```

Этот процесс запускается при отправке коммита в ветку `main`, если он включён и остальные условия выполнены. Создание коммита в локальном терминале не отправляет изменение на GitHub. Этот фрагмент реагирует именно на отправку.

:::single-choice{#ci-workflow-triggers-push-filter} Какое действие подходит под этот триггер push?

::option[Создать коммит в локальной ветке main.]{#ci-workflow-triggers-push-filter-a explanation="Триггер реагирует на событие в репозитории GitHub."}
::option[Отправить коммит в ветку draft.]{#ci-workflow-triggers-push-filter-b explanation="Фильтр выбирает ветку main."}
::option[Отправить коммит в main.]{#ci-workflow-triggers-push-filter-c .correct explanation="Действие соответствует событию push и фильтру ветки."}
:::

## Разбираем триггер пул-реквеста

Другое событие позволяет проверить предлагаемые изменения до их слияния. В этом фрагменте фильтр относится к целевой ветке пул-реквеста.

```yaml
on:
  pull_request:
    branches:
      - main
```

Предложение перенести изменения из `health-page` в `main` подходит под этот фильтр. При стандартном наборе типов активности процесс может запуститься, например, при открытии пул-реквеста или отправке нового коммита в его исходную ветку.

:::single-choice{#ci-workflow-triggers-pr-target} Пул-реквест предлагает включить изменения из notes в main. Какое имя учитывается в фильтре?

::option[Notes, исходная ветка.]{#ci-workflow-triggers-pr-target-b explanation="Notes содержит предлагаемые изменения."}
::option[Целевая ветка main.]{#ci-workflow-triggers-pr-target-a .correct explanation="Фильтр применяется к целевой ветке, которая получит изменения."}
::option[Имя файла, изменённого в пул-реквесте.]{#ci-workflow-triggers-pr-target-c explanation="Этот фрагмент фильтрует по именам веток."}
:::

## Читаем несколько триггеров

В одном файле оба события можно перечислить под ключом `on`. Запуск для пул-реквеста может проверить результат предлагаемого слияния. После слияния, обновившего `main`, запуск по событию push может проверить новое состояние этой ветки. Каждый результат относится к событию и ревизии, указанным в соответствующем запуске.

:::single-choice{#ci-workflow-triggers-after-merge} Рабочий процесс использует оба триггера из примеров. После слияния обновилась main. Какое из событий соответствует этому обновлению?

::option[Отправка изменений в main.]{#ci-workflow-triggers-after-merge-b .correct explanation="Целевая ветка обновилась и подходит под фильтр push."}
::option[Открытие пул-реквеста для новой ветки.]{#ci-workflow-triggers-after-merge-a explanation="В этом примере main обновилась после слияния."}
::option[Локальный коммит без обновления удалённого репозитория.]{#ci-workflow-triggers-after-merge-c explanation="В этом примере ветка main уже изменилась на GitHub."}
:::

## Итоги

Теперь вы можете сопоставить триггер рабочего процесса с событием в репозитории.

1. Читайте условия события push и его фильтр веток.
2. Находите целевую ветку, к которой применяется фильтр пул-реквеста.
3. Связывайте результат запуска с вызвавшим его событием.
