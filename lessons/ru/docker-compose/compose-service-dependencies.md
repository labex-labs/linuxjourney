Вспомогательная программа, которой нужен веб-сервер, может отправить первый запрос слишком рано, даже если сервисы запустились в нужном порядке. **Проверка состояния** — короткий тест, который выполняет Docker. Он показывает, может ли сервис выполнить нужное действие, например ответить на HTTP-запрос.

## Выбираем проверку готовности

В этом отдельном примере проверка выполняется внутри веб-контейнера. Она запрашивает локальную веб-страницу. Если запрос успешен, Docker получает подтверждение, что сервер отвечает из этой точки.

```yaml
services:
  web:
    image: nginx:alpine
    healthcheck:
      test: ["CMD", "wget", "-q", "-O", "/dev/null", "http://127.0.0.1/"]
      interval: 3s
      timeout: 2s
      retries: 5
  toolbox:
    image: busybox:1.36
    command: ["sleep", "3600"]
    depends_on:
      web:
        condition: service_healthy
```

Сохраните пример под именем `compose.health.yaml` в том же учебном каталоге. Проверка запускается через заданные интервалы, и у каждой попытки есть ограничение по времени. Она проверяет локальный ответ внутри веб-контейнера.

:::single-choice{#compose-service-dependencies-check-location} Где выполняется wget при этой проверке состояния?

::option[Внутри веб-контейнера.]{#compose-service-dependencies-check-location-c .correct explanation="Запрос к адресу обратной петли выполняется из этого контейнера."}
::option[В браузере на хосте.]{#compose-service-dependencies-check-location-a explanation="Команду выполняет Docker согласно определению веб-сервиса."}
::option[В контейнере с инструментами.]{#compose-service-dependencies-check-location-b explanation="Проверка задана в разделе web."}
:::

## Ждём готовности сервиса, от которого зависим

Условие `service_healthy` указывает Compose дождаться успешной проверки, прежде чем запускать зависимый контейнер с инструментами. Если указан только порядок запуска, зависимый контейнер может запуститься, как только веб-сервис начнёт выполняться. В этот момент сервер, возможно, ещё не умеет ответить на первый запрос.

```bash
$ docker compose -p journey-health -f compose.health.yaml up -d
$ docker compose -p journey-health -f compose.health.yaml ps
```

В списке проверьте, что web отмечен как исправный, а контейнер с инструментами запущен.

:::single-choice{#compose-service-dependencies-ready-condition} Веб-процесс уже запущен, но локальный запрос ещё завершается ошибкой. Какое условие должно задержать запуск контейнера с инструментами?

::option[Только порядок запуска.]{#compose-service-dependencies-ready-condition-b explanation="Даже если web запустился первым, ему может понадобиться время, чтобы начать отвечать."}
::option[Фоновый режим.]{#compose-service-dependencies-ready-condition-c explanation="Этот режим определяет, как терминал ждёт завершения. Готовность сервиса он не проверяет."}
::option[Условие service_healthy.]{#compose-service-dependencies-ready-condition-a .correct explanation="При таком условии Compose ждёт результата проверки состояния."}
:::

## Разбираемся со сбоем после запуска

Условие запуска в Compose определяет, когда на этапе запуска можно начать работу зависимого сервиса. Исправный на момент запуска сервис может перестать отвечать позже. Клиенту стоит обрабатывать ошибки запросов и подключаться снова, когда нужный сервис станет доступен. Проверьте текущее состояние сервиса и отправьте запрос напрямую.

:::single-choice{#compose-service-dependencies-later-failure} Запрос завершился ошибкой через час после запуска обоих сервисов. Что можно проверить сейчас?

::option[Только исходный порядок запуска.]{#compose-service-dependencies-later-failure-a explanation="Он описывает, что происходило при запуске."}
::option[Текущий результат проверки состояния и запрос из зависимого сервиса.]{#compose-service-dependencies-later-failure-b .correct explanation="Так можно проверить текущее состояние сервиса и путь, по которому обращается клиент."}
::option[Количество образов в кэше Docker.]{#compose-service-dependencies-later-failure-c explanation="Наличие образов мало говорит о том, как отвечает запущенный сервис."}
:::

## Проверяем из двух точек

Успешная локальная проверка показывает, что доступно из самого веб-контейнера. Контейнеру с инструментами по-прежнему нужны сеть проекта и рабочий адрес сервиса. Проверьте результат проверки состояния и отдельно запрос из контейнера с инструментами.

:::single-choice{#compose-service-dependencies-final-application} Проверка состояния успешна, но запрос из контейнера с инструментами завершается ошибкой. Какое сравнение поможет найти причину?

::option[Посмотреть только исходное время запуска.]{#compose-service-dependencies-final-application-b explanation="Время запуска не показывает, какие пути работают сейчас."}
::option[Считать оба запроса успешными, потому что web отмечен как исправный.]{#compose-service-dependencies-final-application-c explanation="Проверка состояния даёт сведения только из одной точки."}
::option[Сравнить один и тот же запрос изнутри web и из контейнера с инструментами к web.]{#compose-service-dependencies-final-application-a .correct explanation="Так можно сравнить доступность изнутри сервиса и по пути, которым действительно пользуется зависимый контейнер."}
:::

## Итоги

Теперь вы можете использовать проверку состояния, чтобы оценить готовность сервиса.

1. Уточняйте, откуда и что проверяет тест.
2. Если одного порядка запуска мало, дождитесь подтверждения готовности.
3. Если сервис откажет позже, проверяйте, как он работает сейчас.
