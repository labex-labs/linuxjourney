Запись каталога даёт inode имя. Жёсткая ссылка создаёт ещё одну запись каталога для того же inode, а символическая — другой inode, содержимым которого является путь для разрешения. Это различие определяет идентичность, срок жизни и поведение между файловыми системами.

## Создание и просмотр символической ссылки

Создайте символическую ссылку командой `ln -s TARGET LINK_NAME`:

```bash
$ printf '%s\n' 'example' > myfile
$ ln -s -- myfile myfilelink
$ ls -li myfile myfilelink
151   -rw-r--r-- 1 user user 8 ... myfile
93403 lrwxrwxrwx 1 user user 6 ... myfilelink -> myfile
```

У символической ссылки собственный inode, где хранится текст `myfile`. Когда программа следует через `myfilelink`, разрешение пути продолжается к цели. Покажите сохранённый текст без следования ссылке:

```bash
$ readlink myfilelink
```

:::single-choice{#symlinks-create-symbolic}
Какая команда создаёт символическую ссылку `myfilelink` с текстом цели `myfile`?

::option[`ln -s -- myfile myfilelink`]{#symlinks-ln-s .correct explanation="Параметр `-s` запрашивает символическую ссылку, после него идут цель и имя новой ссылки."}
::option[`ln -- myfile myfilelink`]{#symlinks-ln-hard explanation="Без `-s` команда `ln` запрашивает жёсткую ссылку на существующий inode."}
::option[`readlink myfile myfilelink`]{#symlinks-readlink-create explanation="Readlink просматривает символическую ссылку, а не создаёт её."}
:::

## Относительные и абсолютные цели

Абсолютная цель начинается с `/`. Относительная цель разрешается относительно каталога, содержащего символическую ссылку, а не текущего каталога оболочки в момент последующего открытия.

```bash
$ mkdir -p tree/data tree/current
$ printf '%s\n' 'value' > tree/data/item
$ ln -s ../data/item tree/current/item
```

Перемещение всей иерархии `tree` сохраняет эту относительную связь. Перемещение только ссылки или цели может её нарушить. Символической ссылке разрешено содержать несуществующую цель; тогда она называется висячей или битой.

:::single-choice{#symlinks-relative-resolution}
Откуда разрешается относительная цель символической ссылки?

::option[Из домашнего каталога создавшего её пользователя.]{#symlinks-creator-home explanation="Идентичность создателя не становится постоянной базой разрешения."}
::option[Из текущего каталога первой оболочки, которая её выводит.]{#symlinks-listing-shell explanation="Контекст вывода не переписывает сохранённую связь цели."}
::option[Из каталога, содержащего символическую ссылку.]{#symlinks-containing-directory .correct explanation="При обходе пути сохранённый относительный текст подставляется в расположении ссылки."}
:::

## Создание жёсткой ссылки

Создайте ещё одно имя существующего обычного файла без `-s`:

```bash
$ ln -- myfile myhardlink
$ ls -li myfile myhardlink
151 -rw-r--r-- 2 user user 8 ... myfile
151 -rw-r--r-- 2 user user 8 ... myhardlink
```

Оба имени относятся к одной файловой системе и номеру inode. Счётчик ссылок становится равен 2. Ни одно имя по своей природе не является «оригиналом»: изменение содержимого через одно имя меняет общий объект, а удаление одного оставляет другое.

Жёсткие ссылки не пересекают границы файловых систем, потому что номер inode имеет смысл только внутри своей системы. Linux также не позволяет обычным пользователям создавать жёсткие ссылки на каталоги и может ограничивать ссылки на чужие файлы, предотвращая циклы и проблемы безопасности.

:::single-choice{#symlinks-hard-link-inode}
Что разделяют две жёсткие ссылки одного обычного файла?

::option[Только похожие имена при отдельных данных файлов.]{#symlinks-separate-data explanation="Это описывает независимые копии, а не жёсткие ссылки."}
::option[Путь, сохранённый внутри отдельного inode символической ссылки.]{#symlinks-stored-path explanation="Текст пути является определяющим механизмом символической ссылки."}
::option[Один inode и содержимое файла.]{#symlinks-same-inode .correct explanation="Каждая запись каталога именует один и тот же объект файловой системы."}
:::

## Срок жизни и удаление

Удаление символической ссылки удаляет объект ссылки, а не её цель:

```bash
$ rm -- myfilelink
```

Удаление имени жёсткой ссылки уменьшает счётчик ссылок общего inode. Файловая система может освободить объект только после обнуления счётчика и исчезновения всех открытых описаний файла и других сохраняющих его ссылок.

Не добавляйте завершающую косую черту при удалении символической ссылки на каталог: в зависимости от команды она может включить семантику следования каталогу. Проверьте ссылку через `ls -ld -- LINK` и осознанно удалите её имя.

:::single-choice{#symlinks-remove-symbolic}
Что обычно происходит при удалении самой символической ссылки?

::option[Удаляются inode и имя ссылки, а цель сохраняется.]{#symlinks-remove-link-only .correct explanation="Удаление символической ссылки не действует на объект, названный сохранённым текстом цели."}
::option[Цель и все её жёсткие ссылки стираются автоматически.]{#symlinks-remove-target explanation="Символическая ссылка — отдельный объект файловой системы и не владеет целью."}
::option[Перед удалением цель копируется внутрь ссылки.]{#symlinks-copy-target explanation="Удаление не сохраняет содержимое цели внутри ссылки."}
:::

## Безопасное следование ссылкам

Символические ссылки могут перенаправить привилегированную программу за пределы ожидаемого каталога или измениться между проверкой и использованием. Защищённые программы должны избегать гонок «проверить, затем открыть» и применять подходящие языку и ОС интерфейсы относительно каталога, без следования или с ограниченным разрешением.

Для обычной проверки:

- `ls -ld LINK` показывает саму ссылку;
- `readlink LINK` выводит сохранённый текст цели;
- `stat LINK` обычно сообщает метаданные ссылки, а `stat -L LINK` следует ей в GNU coreutils;
- `find -L` следует ссылкам и может встретить циклы; используйте его только намеренно.

Разрешения вида `lrwxrwxrwx` не являются общим предоставлением доступа. Доступ определяется обходом каталогов, политикой следования и разрешениями цели; владение ссылкой также важно для некоторых правил защищённых каталогов.

:::single-choice{#symlinks-readlink-output}
Что по умолчанию выводит `readlink LINK`?

::option[Текст пути, сохранённый в символической ссылке.]{#symlinks-readlink-target-text .correct explanation="Команда просматривает объект ссылки, не читая содержимое целевого файла."}
::option[Полное байтовое содержимое целевого обычного файла.]{#symlinks-readlink-file-content explanation="Для содержимого цели после осознанного разрешения используйте команду чтения файла."}
::option[Все жёсткие ссылки во всей файловой системе.]{#symlinks-readlink-all-hard explanation="Для поиска жёстких ссылок нужен учитывающий inode поиск, не связанный с текстом цели символической ссылки."}

## Итоги

Теперь вы можете выбирать и проверять правильный вид ссылки файловой системы.

1. Использовать `ln -s TARGET LINK` для основанной на пути символической ссылки.
2. Разрешать относительные цели из каталога, содержащего ссылку.
3. Использовать `ln EXISTING LINK` для ещё одного имени inode в той же файловой системе.
4. Отличать удаление символической ссылки от удаления жёсткой.
5. Избегать небезопасного следования ссылкам в привилегированных и рекурсивных операциях.
