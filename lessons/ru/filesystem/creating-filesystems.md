Создание файловой системы записывает на блочное устройство новые структуры распределения и метаданных. Это разрушительная инициализация, а не простая смена метки. Для практики используйте только одноразовое хранилище, а перед форматированием устройства с ценными данными имейте проверенную резервную копию.

## Понимание `mkfs`

`mkfs` обычно служит интерфейсом, который вызывает программу конкретной файловой системы: `mkfs.ext4`, `mkfs.xfs` или `mkfs.btrfs`. Общая форма команды:

```bash
$ sudo mkfs -t ext4 /dev/VERIFIED-PARTITION
```

Заменяйте заполнитель только после проверки. Эквивалентный синтаксис конкретного формата обычно выглядит так:

```bash
$ sudo mkfs.ext4 /dev/VERIFIED-PARTITION
```

Поддерживаемые параметры, значения по умолчанию, наборы возможностей и запросы на перезапись различаются между реализациями. Читайте локальное руководство точной программы форматирования и не считайте, что все реализации `mkfs` ведут себя одинаково.

::option[Монтирование существующей файловой системы без изменений.]{#creating-filesystems-mount-existing explanation="Монтирование — отдельная операция; mkfs инициализирует метаданные на устройстве."}

::option[Вывод всех смонтированных файловых систем.]{#creating-filesystems-list-mounted explanation="Инвентаризацию монтирований только для чтения выполняют такие инструменты, как `findmnt`."}
:::

## Проверка каждого уровня хранилища

До форматирования определите цель по модели, серийному номеру, размеру, топологии, постоянной ссылке и назначению:

```bash
$ lsblk -o NAME,PATH,TYPE,SIZE,MODEL,SERIAL,FSTYPE,UUID,MOUNTPOINTS
$ findmnt --real
$ sudo wipefs --no-act /dev/VERIFIED-PARTITION
```

`wipefs --no-act` сообщает распознанные сигнатуры, не стирая их. Также проверьте использование в swap, LVM, RAID, шифровании, виртуальных машинах, контейнерах и приложениях. Устройство может быть активно даже при пустом `MOUNTPOINTS`.

Размонтируйте или деактивируйте каждый связанный уровень его собственным инструментом. Непосредственно перед форматированием снова проверьте идентичность, поскольку имена перечисления могут меняться.

:::single-choice{#creating-filesystems-wipefs-no-act} Что даёт `wipefs --no-act TARGET` в этом процессе?

::option[Отчёт только для чтения о распознанных сигнатурах.]{#creating-filesystems-signature-report .correct explanation="Режим no-act помогает увидеть существующие сигнатуры файловой системы, таблицы разделов, RAID и другие, не удаляя их."}
::option[Новую пустую файловую систему, готовую к монтированию.]{#creating-filesystems-wipefs-formats explanation="Проверка сигнатур не инициализирует новую файловую систему."}
::option[Гарантию, что ни один процесс не использует цель.]{#creating-filesystems-wipefs-no-users explanation="Использование нужно отдельно проверять среди монтирований и во всём стеке хранилища."}
:::

## Осознанный выбор файловой системы

Выберите тип, поддерживаемый дистрибутивом, загрузочной средой, средствами резервного копирования и восстановления и подходящий нагрузке. Учитывайте необходимые пределы, снимки, контрольные суммы, квоты, уровни шифрования, поведение при увеличении и уменьшении и межплатформенный доступ.

Не выбирайте формат лишь по популярности. Например, ext4, XFS и Btrfs различаются эксплуатационными возможностями и процедурами восстановления. Для съёмного устройства обмена может понадобиться другой формат с иной семантикой разрешений Unix.

:::single-choice{#creating-filesystems-type-choice} На чём разумно основывать выбор типа файловой системы?

::option[На самом коротком для ввода названии.]{#creating-filesystems-shortest-name explanation="Длина команды ничего не говорит о надёжности, возможностях или поддержке."}
::option[На обещании полного отсутствия будущих отказов хранилища.]{#creating-filesystems-no-failure explanation="Ни одна файловая система не устраняет отказы оборудования и необходимость резервных копий."}
::option[На потребностях нагрузки и поддерживаемых средствах резервирования, загрузки и восстановления.]{#creating-filesystems-supported-workflow .correct explanation="Формат должен соответствовать техническим требованиям и способности среды эксплуатировать и восстанавливать его."}
:::

## Метки, UUID и проверка

Программы форматирования обычно создают UUID файловой системы и часто позволяют задать понятную человеку метку. Используйте достаточно уникальные для среды метки и следите, чтобы клонированные файловые системы не сохраняли конфликтующие идентификаторы при совместном монтировании.

После успешного создания проверьте систему без монтирования:

```bash
$ lsblk -f /dev/VERIFIED-PARTITION
$ sudo blkid /dev/VERIFIED-PARTITION
```

Запишите UUID для последующей конфигурации монтирования. Создание файловой системы не монтирует её, не создаёт каталоги приложений, не восстанавливает резервные копии и не обеспечивает постоянное монтирование при загрузке.

:::single-choice{#creating-filesystems-after-mkfs} Какой шаг остаётся отдельным после создания файловой системы?

::option[Монтирование в предназначенный каталог.]{#creating-filesystems-mount-separate .correct explanation="Форматирование записывает структуры файловой системы, а монтирование присоединяет её к видимому дереву каталогов."}
::option[Предоставление блочному устройству какой-либо ёмкости.]{#creating-filesystems-capacity explanation="Нижележащий раздел или логическое устройство уже предоставляет форматируемую ёмкость."}
::option[Создание с нуля каталога ядра `/dev`.]{#creating-filesystems-create-dev explanation="Управление узлами устройств не зависит от форматирования одной цели."}
:::

## Итоги

Теперь вы можете описать создание файловой системы как проверенную разрушительную операцию.

1. Считать `mkfs` диспетчером инструментов конкретных форматов.
2. Проверять постоянную идентичность, сигнатуры и каждого активного потребителя.
3. Выбирать файловую систему по требованиям поддержки и восстановления.
4. Проверять созданные тип, метку и UUID до монтирования.
