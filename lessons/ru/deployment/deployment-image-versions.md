Тег вроде `site:2` делает ссылку на образ понятнее. При публикации замены тег можно переназначить. Чтобы точно определить содержимое образа, запишите его **дайджест** — значение, вычисленное по содержимому, на которое указывает ссылка.

## Как читать тег

Представьте, что в разные дни реестр показывает такие записи. Дайджесты в примере сокращены для наглядности. Скачать образ по таким значениям нельзя.

```text
Monday    site:2    sha256:a1b2…
Tuesday   site:2    sha256:c3d4…
```

Тот же тег теперь указывает на другое содержимое. Машина, скачавшая образ в понедельник, может по-прежнему использовать старый образ.

:::single-choice{#deployment-image-versions-moving-tag} В обоих окружениях указан тег site:2. По чему можно узнать, какой образ скачали в каждом из них?

::option[Только по общему тегу.]{#deployment-image-versions-moving-tag-b explanation="В примере у двух разных образов один и тот же тег."}
::option[По количеству контейнеров на каждой машине.]{#deployment-image-versions-moving-tag-c explanation="Число контейнеров не позволяет узнать, из каких образов они созданы."}
::option[По записанным дайджестам.]{#deployment-image-versions-moving-tag-a .correct explanation="Тег можно переназначить, а дайджест указывает на содержимое, выбранное при скачивании."}
:::

## Как читать ссылку с дайджестом

В ссылке на образ после знака `@` может стоять полный дайджест. По такой ссылке реестр выдаёт конкретный объект. Возьмите полный дайджест из реестра или записи о сборке. Сокращённые значения удобны в примерах, но для скачивания образа их недостаточно.

:::single-choice{#deployment-image-versions-fixed-reference} Какая форма ссылки указывает на конкретный объект реестра?

::option[Имя образа без тега.]{#deployment-image-versions-fixed-reference-a explanation="Docker подставит тег по умолчанию, который может быть переназначен."}
::option[Имя образа с полным дайджестом.]{#deployment-image-versions-fixed-reference-c .correct explanation="Дайджест указывает на конкретное содержимое."}
::option[Комментарий с датой сборки.]{#deployment-image-versions-fixed-reference-b explanation="Реестр не может найти объект по комментарию."}
:::

## Как сравнивать образы одной платформы

Имя образа может указывать на список сборок для разных типов машин или на один образ для конкретной платформы. Сравнивая, что фактически запущено на двух хостах, запишите платформу каждого хоста и сравните ссылки на образы для соответствующей платформы. Сохраните исходную полную ссылку в записи о выпуске.

:::single-choice{#deployment-image-versions-compare-platform} Выпуск поддерживает arm64 и amd64. Что стоит сравнить при проверке двух хостов с amd64?

::option[Ссылки на образы для amd64, которые выбрали оба хоста.]{#deployment-image-versions-compare-platform-b .correct explanation="Так вы сравните содержимое для одной и той же платформы."}
::option[Образы для разных архитектур.]{#deployment-image-versions-compare-platform-a explanation="Эти объекты рассчитаны на разные платформы."}
::option[Имена хостов.]{#deployment-image-versions-compare-platform-c explanation="Имена обозначают хосты, по ним нельзя определить, что на них развёрнуто."}
:::

## Итоги

Теперь вы можете определить точный образ, даже если тег впоследствии изменился.

1. Объяснить, почему один тег может указывать на разное содержимое.
2. Распознать ссылку с полным дайджестом.
3. Выбрать для сравнения образы нужной платформы.
