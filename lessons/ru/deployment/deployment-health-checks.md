Программа может уже работать, хотя ещё не готова принимать запросы. Проверяйте сервис поэтапно, чтобы понимать, что именно подтвердил каждый результат.

## Проверка процесса

По списку контейнеров можно узнать, запущена ли основная программа. Это важная первая проверка после развёртывания. По списку нельзя определить, завершилась ли подготовка программы к работе и доступна ли она из браузера.

:::single-choice{#deployment-health-checks-process-scope} Новый контейнер находится в состоянии Up. Какой вывод можно сделать?

::option[Посетители точно получают новую страницу.]{#deployment-health-checks-process-scope-a explanation="Состояние контейнера ничего не говорит о результате запроса посетителя."}
::option[На момент проверки основная программа контейнера работает.]{#deployment-health-checks-process-scope-b .correct explanation="Состояние Up показывает, что процесс запущен."}
::option[Все зависимости успешно прошли проверку.]{#deployment-health-checks-process-scope-c explanation="В списке нет результатов проверок зависимостей."}
:::

## Проверка ответа сервиса

**Конечная точка** — это адрес и путь, по которым сервис обрабатывает запросы. Выберите путь, который позволяет проверить нужную функцию. Для практики на своём компьютере используйте пустую папку. Перенаправление вывода создаст файл с номером версии. Оставьте сервер Python запущенным на адресе обратной петли в этом терминале. После упражнения остановите его сочетанием Ctrl+C.

```bash
$ mkdir site
$ printf '%s\n' 2 > site/version.txt
$ python3 -m http.server 8091 --bind 127.0.0.1 --directory site
```

Во втором терминале запросите файл с номером версии. Параметр `-f` заставляет curl считать ответ HTTP с кодом ошибки неудачей, а `-sS` скрывает индикатор выполнения и по-прежнему показывает ошибки.

```bash
$ curl -fsS http://127.0.0.1:8091/version.txt
```

В упражнении ожидается результат `2`. Успешный запрос файла с номером версии проверяет лишь одну небольшую часть работы сайта.

:::single-choice{#deployment-health-checks-endpoint-mismatch} Запрос выполнен и вывел 1. Что нужно выяснить?

::option[Какая версия отвечает по этому адресу.]{#deployment-health-checks-endpoint-mismatch-a .correct explanation="Сетевой запрос прошёл, но ответила другая версия."}
::option[Почему curl вообще не может подключиться.]{#deployment-health-checks-endpoint-mismatch-b explanation="Полученное значение показывает, что удалось подключиться и получить ответ."}
::option[Есть ли цифра в имени сервиса.]{#deployment-health-checks-endpoint-mismatch-c explanation="По имени сервиса нельзя определить, какая версия ответила."}
:::

## Проверка со стороны клиента

Если запрос с хоста сервиса проходит, повторите безопасную проверку оттуда, откуда обычно подключаются пользователи. Балансировщик нагрузки, прокси или сетевое правило могут изменить маршрут запроса. Запишите адрес проверки и полученный ответ. Если результат расходится с ожидаемым для выпуска, продолжите разбираться в развёртывании.

:::single-choice{#deployment-health-checks-user-path} Локальный запрос возвращает 2, а запрос к общедоступному тестовому адресу — 1. Что стоит проверить дальше?

::option[Сколько строк вывел локальный запрос.]{#deployment-health-checks-user-path-a explanation="Число строк не показывает, что отвечает по общедоступному адресу."}
::option[Повторить только ту же локальную проверку.]{#deployment-health-checks-user-path-b explanation="Локальный запрос уже показал версию 2."}
::option[Какая версия сервиса обрабатывает запросы по общедоступному адресу.]{#deployment-health-checks-user-path-c .correct explanation="Запросы по двум путям дали разные ответы."}
:::

## Итоги

Теперь вы можете объяснить, что подтверждает каждая проверка после развёртывания.

1. Убедиться, что основная программа запущена.
2. Отправить запрос по адресу, который должен вернуть ожидаемую версию.
3. Отдельно проверить путь запроса со стороны пользователя.
