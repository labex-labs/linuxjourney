Коллега говорит, что версия 2 готова. Возможно, её файлы уже собраны, версию одобрили или она уже доступна посетителям. Посмотрите записи, чтобы выяснить, до какого этапа дошла работа.

## Как найти сборку

При сборке из конкретной ревизии исходного кода получают готовый результат. В примере небольшой сайт упаковывают в образ контейнера и сохраняют в реестре образов. Запишите ссылку на полученный образ рядом с исходным коммитом.

```text
Build 81
Source commit: 3ab4501
Image: registry.example/journey/site:2
Result: succeeded
```

Из этой записи видно, что собрали. На сайте всё ещё может работать более ранняя версия.

:::single-choice{#build-release-deploy-build-record} Какая запись связывает собранный образ с ревизией исходного кода?

::option[Закладка в браузере.]{#build-release-deploy-build-record-b explanation="В закладке хранится адрес, но по ней нельзя узнать, как были собраны файлы."}
::option[Сборка 81.]{#build-release-deploy-build-record-a .correct explanation="В записи указаны и исходный коммит, и полученный образ."}
::option[Имя последней локальной ветки.]{#build-release-deploy-build-record-c explanation="Ветка может указывать на другой коммит и не позволяет однозначно определить эту сборку."}
:::

## Как читать запись о выпуске

**Выпуск** указывает, какую версию одобрили для распространения. Например, запись о выпуске может подтверждать, что для испытательного окружения одобрен именно образ из сборки 81. После одобрения можно ссылаться на этот же артефакт без повторной сборки.

:::single-choice{#build-release-deploy-release-record} Выпуск 2 одобрен для испытательного окружения. Что это подтверждает?

::option[Указанный артефакт разрешено использовать в этом окружении.]{#build-release-deploy-release-record-b .correct explanation="В записи о выпуске указано, какой артефакт одобрили для испытательного окружения."}
::option[Версия 2 уже обслуживает запросы во всех окружениях.]{#build-release-deploy-release-record-a explanation="Одобрение позволяет перейти к следующему этапу. По нему нельзя узнать, какая версия запущена."}
::option[Версия 2 обрабатывает больше запросов в секунду.]{#build-release-deploy-release-record-c explanation="Запись о выпуске не содержит замеров трафика."}
:::

## Как определить развёрнутую версию

При **развёртывании** конкретную версию помещают в выбранное окружение, где запускают или обновляют приложение. У каждого окружения, например испытательного или рабочего, свои настройки и ресурсы. Запрос к адресу, по которому приложение сообщает номер версии, поможет узнать, какая версия там отвечает.

```text
Staging version response: 2
Production version response: 1
```

В этом примере в испытательном окружении отвечает новая версия, а в рабочем по-прежнему работает версия 1.

:::single-choice{#build-release-deploy-running-version} Нужно подтвердить, что в рабочем окружении отвечает версия 2. Какое наблюдение поможет это проверить?

::option[Ещё один ответ с версией 2 из испытательного окружения.]{#build-release-deploy-running-version-a explanation="Так вы снова проверите только испытательное окружение."}
::option[Сообщение об одобрении выпуска.]{#build-release-deploy-running-version-b explanation="Одобрение само по себе ничего не говорит о запущенном сервисе."}
::option[Ответ с номером версии, полученный с адреса рабочего окружения.]{#build-release-deploy-running-version-c .correct explanation="Так вы проверите именно то окружение, о котором спросили."}
:::

## Итоги

Теперь вы можете различать записи, которые появляются на пути от сборки до развёртывания.

1. Связать результат сборки с исходным кодом.
2. Определить, какой артефакт одобрен для выпуска.
3. Убедиться, что в нужном окружении отвечает ожидаемая версия.
