Контейнер `preview` завершился. В списке контейнеров видны его состояние и код завершения. Чтобы узнать, что сообщила программа, прочитайте вывод, который Docker собрал для этого контейнера.

## Выбор контейнера

Передайте имя контейнера команде `docker logs`. Она может прочитать сохранённый вывод остановленного контейнера, если тот ещё существует. В этом примере короткая задача перед завершением пыталась прочитать файл `/site/title.txt`.

```text
$ docker logs preview
cat: can't open '/site/title.txt': No such file or directory
```

Файл пыталась прочитать команда `cat`. В сообщении указан путь, который она не смогла найти внутри контейнера.

:::single-choice{#docker-logs-command-read-exited} Контейнеры preview и report использовали один образ. Какая команда читает вывод preview?

::option[`docker logs report`]{#docker-logs-command-exited-report explanation="Имя выбирает один контейнер. Report обозначает другой запуск."}
::option[`docker logs busybox:1.36`]{#docker-logs-command-exited-image explanation="Это ссылка на образ. Журнал принадлежит конкретному контейнеру, созданному из этого образа."}
::option[`docker logs preview`]{#docker-logs-command-exited-preview .correct explanation="Здесь указано имя контейнера, чей вывод нужно прочитать."}
:::

## Как читать сообщение в контексте

В журналах остаются сообщения самой программы. Сообщение о запуске может показывать, что программа начала принимать запросы. Ошибка может назвать операцию, которую не удалось выполнить. В примере `preview` сообщает об отсутствующем пути внутри контейнера. Стоит проверить, должен ли файл находиться именно по этому пути. Сообщение даёт конкретную отправную точку.

:::single-choice{#docker-logs-command-error-boundary} Какой вывод можно сделать из сообщения об отсутствующем файле?

::option[Файл отсутствует во всех каталогах хоста.]{#docker-logs-command-error-host-path explanation="Программа искала путь внутри контейнера. Сообщение не описывает все файлы на хосте."}
::option[Программа не нашла указанный файл внутри preview.]{#docker-logs-command-error-container-path .correct explanation="Сообщение описывает результат поиска файла программой в preview."}
::option[Браузер на хосте использовал неопубликованный порт.]{#docker-logs-command-error-network explanation="Сообщение касается поиска файла. О порте браузера оно ничего не говорит."}
:::

## Последние строки вывода

Если у контейнера много строк вывода, задайте число после `--tail`. Docker вернёт не больше этого количества строк с конца собранного вывода. Начните с небольшого числа. Если первая ошибка находится выше, увеличьте его.

```bash
$ docker logs --tail 5 web
```

![Терминал LabEx с сообщением об отсутствующем файле в preview и последними пятью строками журнала web](https://cdn.jsdelivr.net/gh/labex-labs/linuxjourney@master/images/lessons/docker/docker-logs-command/preview-and-tail.png)

Эти две команды читают вывод разных контейнеров. В примере LabEx `preview` сообщает об отсутствующем файле, а `web` — о запуске Nginx.

:::single-choice{#docker-logs-command-tail-choice} Вы хотите увидеть только две последние доступные строки вывода web. Какая команда подходит?

::option[`docker logs --tail 2 web`]{#docker-logs-command-tail-two .correct explanation="Tail 2 запрашивает до двух строк с конца вывода контейнера."}
::option[`docker logs --tail 5 web`]{#docker-logs-command-tail-five explanation="Эта команда запрашивает до пяти строк и может показать больше двух."}
::option[`docker logs web`]{#docker-logs-command-tail-unlimited explanation="Без ограничения Docker может вернуть все доступные строки."}
:::

## Что делать, если вывод пуст

Docker показывает только то, что удалось собрать. Команда может работать без сообщений, а программа может писать в файл, который Docker не собирает. Если `docker logs` выполнена успешно, но ничего не вывела, проверьте состояние через `docker ps -a`. Сам по себе пустой журнал не говорит о состоянии контейнера.

:::single-choice{#docker-logs-command-empty-result} У задачи cleanup нет строк в журнале. Как узнать, продолжает ли она работать или уже завершилась?

::option[Запросить у Docker больше строк вывода cleanup.]{#docker-logs-command-empty-more-lines explanation="Изменение числа строк не покажет, завершилась ли программа, которая ничего не выводит."}
::option[Найти образ, из которого запустили cleanup.]{#docker-logs-command-empty-image explanation="Образ определяет исходные файлы и настройки. Состояние видно в списке контейнеров."}
::option[Проверить состояние cleanup в полном списке контейнеров.]{#docker-logs-command-empty-container-state .correct explanation="В полном списке есть и запущенные контейнеры, и завершившиеся, которые ещё существуют."}
:::

## Итоги

Теперь вы можете использовать вывод контейнера, чтобы решить, что проверять дальше.

1. Прочитать сохранённый вывод контейнера по имени, даже если он завершился.
2. Использовать сообщение программы, чтобы найти место ошибки.
3. Ограничить вывод с помощью `--tail`.
4. Выбрать отдельную проверку, если журнал не отвечает на вопрос.
