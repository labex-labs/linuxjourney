Проверки авторизации Linux действуют на учётные данные процесса, а не непосредственно на введённое имя пользователя. У процесса есть несколько связанных идентификаторов пользователя и группы, каждый со своей ролью. У большинства обычных программ идентификаторы при запуске совпадают, а привилегированные программы могут намеренно использовать разные значения.

## Действительный идентификатор пользователя

Действительный идентификатор пользователя обозначает учётную запись, запустившую процесс, или исходный сеанс входа его предка. Программы могут обращаться к нему, чтобы отличать вызывающую сторону от повышенного эффективного идентификатора.

У обычной команды, запущенной пользователем Bob, действительный идентификатор обычно равен UID Bob. Создание другого процесса само по себе не создаёт новую учётную запись и не меняет этот идентификатор.

:::single-choice{#process-permissions-real-uid} Что обычно обозначает действительный идентификатор пользователя процесса?

::option[Владельца последнего открытого файла.]{#process-permissions-real-opened-file explanation="Открытие файла не заменяет действительный UID процесса владельцем этого файла."}
::option[Учётную запись, связанную с исходной вызывающей стороной процесса.]{#process-permissions-real-caller .correct explanation="Действительный UID записывает идентификатор вызывающего пользователя, унаследованный при запуске процесса."}
::option[Группу, выбранную для каждой проверки доступа.]{#process-permissions-real-group explanation="UID — идентификатор пользователя; групповые проверки используют отдельные групповые учётные данные."}
:::

## Эффективный идентификатор пользователя

Эффективный идентификатор пользователя — это пользовательские учётные данные, применяемые во многих проверках файловой системы и привилегий. Обычно он совпадает с действительным UID. Выполнение учитываемой setuid-программы может вместо этого инициализировать его владельцем исполняемого файла.

Например, тщательно разработанная утилита паролей может работать с повышенным эффективным UID для обновления защищённых данных аутентификации. При этом программа всё равно должна обеспечивать политику с учётом вызывающей стороны, запрошенной учётной записи, результатов PAM и другого контекста. Наличие эффективного UID не делает автоматически законной любую запрошенную операцию.

:::single-choice{#process-permissions-effective-uid} Какой идентификатор пользователя применяется во многих решениях управления доступом от имени процесса?

::option[Эффективный идентификатор пользователя.]{#process-permissions-effective-active .correct explanation="Эффективный UID — активные пользовательские учётные данные, используемые во многих проверках авторизации."}
::option[Только сохранённый идентификатор пользователя.]{#process-permissions-effective-saved-only explanation="Сохранённый идентификатор поддерживает переходы учётных данных, но обычно не является активным для проверок доступа."}
::option[UID, сохранённый у текущего каталога.]{#process-permissions-effective-directory explanation="Владение файловой системы — метаданные объекта, а не активные пользовательские учётные данные процесса."}
:::

## Сохранённый set-user-ID

Сохранённый set-user-ID позволяет программе удерживать идентификатор, который она сможет позднее восстановить в соответствии с правилами системных вызовов. Привилегированная программа может временно переключить эффективный UID на менее привилегированное значение, выполнить обычную работу с ограниченными полномочиями и восстановить сохранённый идентификатор только для узкой операции.

Это безопаснее постоянного сохранения повышенных полномочий на протяжении всей программы, но лишь при правильной реализации. Программы должны окончательно отбрасывать привилегии, когда они больше не нужны, и проверять каждую операцию изменения учётных данных на ошибку.

:::single-choice{#process-permissions-saved-uid} Зачем привилегированной программе сохранять set-user-ID?

::option[Чтобы переключать эффективный идентификатор для контролируемых привилегированных и непривилегированных этапов.]{#process-permissions-saved-switch .correct explanation="Сохранённый идентификатор может поддерживать временное снижение привилегий и разрешённое последующее восстановление."}
::option[Чтобы автоматически назначать этот UID каждому прочитанному файлу.]{#process-permissions-saved-file-owner explanation="Чтение файла не меняет его владельца на сохранённый UID процесса."}
::option[Чтобы заменить системную базу учётных записей для процесса.]{#process-permissions-saved-database explanation="Учётные данные процесса не заменяют записи учётных записей или данные службы имён."}
:::

## Идентификаторы пользователей — лишь часть набора учётных данных

У процессов также есть действительные, эффективные, сохранённые и дополнительные групповые учётные данные. На авторизацию дополнительно могут влиять идентификаторы файловой системы, capabilities, пространства имён, модули безопасности, ACL, параметры подключения и политики служб. Поэтому утверждение «UID это разрешает» часто объясняет лишь часть полного решения.

Для проверки учётных данных в Linux используйте такие инструменты, как `ps` и `/proc/PROCESS/status`. Наличие полей и форматы отображения различаются, поэтому обращайтесь к локальной документации и не меняйте учётные данные только ради эксперимента в общей системе.

:::single-choice{#process-permissions-ordinary-identities} Как обычно соотносятся действительный и эффективный UID у большинства обычных команд без перехода привилегий?

::option[Эффективный UID всегда равен нулю.]{#process-permissions-effective-root explanation="Обычные команды не получают UID root автоматически."}
::option[Действительный UID всегда равен владельцу исполняемого файла.]{#process-permissions-real-file-owner explanation="Владелец исполняемого файла влияет на поведение setuid, а не на обычный действительный UID."}
::option[Они обычно совпадают с UID вызвавшего пользователя.]{#process-permissions-uids-match .correct explanation="Без setuid или явного изменения учётных данных обычные процессы обычно работают с совпадающими действительным и эффективным идентификаторами."}
:::

## Итоги

Теперь вы можете объяснить, почему процесс Linux хранит несколько пользовательских идентификаторов.

1. Используйте действительный UID для определения исходной вызывающей стороны.
2. Связывайте эффективный UID с активными проверками авторизации.
3. Используйте сохранённый идентификатор для понимания контролируемых переходов привилегий.
4. Учитывайте идентификаторы групп и дополнительные механизмы безопасности как часть полного решения.
