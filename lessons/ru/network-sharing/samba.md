Samba реализует протокол Server Message Block в Unix-подобных системах и позволяет клиентам Linux, Windows, macOS и других систем совместно использовать файлы и принтеры. Современные установки применяют актуальные диалекты SMB; старый термин CIFS всё ещё встречается в клиентских инструментах Linux, но не является поводом включать устаревший SMB1.

## Планирование общего ресурса

Перед установкой или изменением Samba определите разрешённых клиентов, идентификаторы, потребности в чтении и записи, сетевую зону, владельца данных, политику резервного копирования и требуемый диалект SMB. Используйте отдельный каталог, чтобы случайно не открыть домашнее или системное дерево.

Доступ регулируют и политика Samba, и нижележащие права файловой системы. Разрешение записи в `smb.conf` не может предоставить учётной записи отсутствующий у неё доступ к файловой системе.

## Определение простого общего ресурса

Основная конфигурация обычно находится в `/etc/samba/smb.conf`. Пример с ограниченным доступом:

```ini
[team]
    path = /srv/samba/team
    browseable = yes
    read only = no
    valid users = @teamshare
```

Создайте каталог и примените проверенные владельца и права для группы Unix:

```bash
$ sudo install -d -o root -g teamshare -m 2770 /srv/samba/team
```

Бит set-group-ID помогает новым записям наследовать группу каталога, однако для совместного доступа также могут понадобиться ACL или тщательно подобранная маска создания. Проверяйте фактический результат для файлов и каталогов, а не полагайтесь лишь на наследование.

:::single-choice{#samba-valid-users} Что выражает `valid users = @teamshare`?

::option[Каждый анонимный сетевой пользователь получает доступ на запись.]{#samba-every-anonymous explanation="Правило ограничивает доступ, а не включает гостевую запись."}
::option[Сервер должен переименовать общий ресурс в `teamshare`.]{#samba-rename-share explanation="Отображаемым именем ресурса остаётся имя раздела `[team]`."}
::option[Правило ресурса разрешает доступ только членам указанной группы.]{#samba-valid-group .correct explanation="Форма с `@` обозначает группу в синтаксисе списка пользователей Samba."}
:::

## Настройка идентификации

В автономной конфигурации Samba учётной записи обычно нужны соответствующий идентификатор Unix и включённые учётные данные Samba:

```bash
$ sudo smbpasswd -a alice
```

Установки с доменной службой каталогов используют другую схему идентификации. Не помещайте пароли в историю оболочки или конфигурацию, доступную посторонним пользователям, и не считайте, что пароль Samba автоматически совпадает с паролем учётной записи Unix.

::option[Удаляет домашний каталог пользователя Unix.]{#samba-delete-home explanation="Команда управляет учётными данными Samba и не удаляет домашние каталоги."}

## Проверка и применение конфигурации

До перезагрузки служб проверьте разобранную конфигурацию:

```bash
$ testparm -s
```

Изучите неожиданные значения по умолчанию и ошибки, затем перезагрузите службу Samba своего дистрибутива через диспетчер служб. Имена различаются; часто встречаются `smbd.service` и `smb.service`. Если поддерживается reload, он нарушает работу меньше, чем restart, однако всё равно проверьте состояние, прослушиваемые сокеты, область межсетевого экрана и журналы.

Выполните тест с клиента, явно указав пользователя:

```bash
$ smbclient //server.example.net/team -U alice
```

:::single-choice{#samba-testparm-purpose} Зачем запускать `testparm -s` перед применением изменения Samba?

::option[Команда копирует каждый общий файл на резервный сервер.]{#samba-testparm-backup explanation="Инструмент разбирает и выводит конфигурацию, а не копирует данные ресурсов."}
::option[Команда проверяет и отображает фактическую конфигурацию Samba.]{#samba-testparm-validate .correct explanation="Вывод анализатора обнаруживает ошибки и показывает интерпретированные параметры до воздействия на службу."}
::option[Команда предоставляет всем клиентам административные права.]{#samba-testparm-admin explanation="Проверка не изменяет авторизацию клиентов."}
:::

## Подключение из Linux

Клиенты Linux обычно используют драйвер файловой системы `cifs` и вспомогательные средства mount. Не указывайте пароли в командной строке: аргументы могут попасть в историю или стать видны при просмотре процессов. Используйте доступный только root файл учётных данных или одобренный механизм хранения:

```bash
$ sudo mount -t cifs //server.example.net/team /mnt/team \
    -o credentials=/root/.smb-team,vers=3.1.1
```

Защитите файл учётных данных, проверьте поддерживаемый обеими сторонами диалект и осознанно задайте требования к UID, GID, правам и шифрованию. После подключения проверьте ресурс через `findmnt`, выполните разрешённые тесты чтения и записи, а затем отключите его, предварительно скоординировав активных пользователей.

:::single-choice{#samba-command-line-password} Почему не следует указывать `password=...` прямо в команде подключения?

::option[Секрет может раскрыться через историю или аргументы процесса.]{#samba-password-exposure .correct explanation="Защищённый источник учётных данных снижает риск случайного раскрытия, хотя его права также требуют внимания."}
::option[SMB вообще не поддерживает аутентификацию паролями.]{#samba-no-passwords explanation="Аутентификация SMB паролем распространена, хотя существуют и другие системы идентификации."}
::option[Этот параметр навсегда делает ресурс доступным только для чтения.]{#samba-password-readonly explanation="Место хранения секрета не определяет политику записи."}
:::

## Итоги

Теперь вы можете настроить общий ресурс Samba с учётом безопасности протокола и файловой системы.

1. Сначала определяйте клиентов, идентификаторы, область сети и политику данных.
2. Ограничивайте общий ресурс и согласовывайте нижележащие права.
3. Управляйте учётными данными Samba в соответствии с моделью идентификации.
4. Проверяйте конфигурацию через `testparm` и выполняйте сквозной клиентский тест.
5. Защищайте клиентские учётные данные и проверяйте подключённый доступ.
