Сервис может ждать соединений на конкретном адресе и порте. **Слушающий сокет** готов принимать входящие соединения. По его адресу можно предварительно судить о том, кто сможет к нему подключиться.

## Список слушающих сокетов TCP

Выполните на учебном хосте Linux эту команду, которая только читает данные. Параметры указывают `ss` показать слушающие сокеты TCP с числовыми адресами и портами.

```bash
$ ss -lnt
```

Посмотрите на столбец локального адреса. В примере для веб-просмотра используется `127.0.0.1:8091`. Номер порта — 8091. Это **адрес обратной петли** (loopback), то есть адрес самого хоста.

:::single-choice{#linux-listening-services-local-listener} Браузеру на том же хосте нужно открыть предварительный просмотр. Какой адрес использовать?

::option[0.0.0.0:8091.]{#linux-listening-services-local-listener-a explanation="Эта запись используется при настройке прослушивания. В примере локальный адрес назначения другой."}
::option[127.0.0.1:8091.]{#linux-listening-services-local-listener-b .correct explanation="Сервис слушает указанный адрес обратной петли и порт."}
::option[Порт 80 на другом сервере.]{#linux-listening-services-local-listener-c explanation="В примере сервис слушает порт 8091 на своём хосте."}
:::

## Что означает прослушивание всех интерфейсов

Локальный IPv4-адрес `0.0.0.0:8091` означает, что сервис слушает на всех IPv4-интерфейсах хоста. Среди них может быть интерфейс, доступный с другого компьютера. Список сокетов показывает, где процесс принимает соединения локально. Правила межсетевого экрана и маршруты могут ограничить доступ с других компьютеров.

:::single-choice{#linux-listening-services-all-interfaces} Сервис меняет адрес с 127.0.0.1 на 0.0.0.0 при том же порте. Что изменилось?

::option[Он может слушать на большем числе интерфейсов IPv4.]{#linux-listening-services-all-interfaces-a .correct explanation="Настройка расширяет набор локальных адресов, на которых можно принимать входящие соединения."}
::option[Он теперь слушает другой порт.]{#linux-listening-services-all-interfaces-b explanation="Номер порта остался прежним."}
::option[Он гарантированно стал доступен из любой сети.]{#linux-listening-services-all-interfaces-c explanation="Доступные пути по-прежнему зависят от сетевых правил и маршрутов."}
:::

## Как проверить нужный путь

Внутренний сервис для сотрудников может быть предназначен для одной сети. Проверьте доступ из этой сети. Если нужно подтвердить ограничение, выполните ещё одну проверку из согласованной точки вне сети. Убедитесь, что работает и сокет, и путь к нему. По одному локальному списку нельзя узнать, что видит удалённый клиент.

:::single-choice{#linux-listening-services-verify-from-client} Вы видите сокет, который слушает на всех локальных интерфейсах. Как проверить его доступность с компьютера сотрудника?

::option[Ещё раз прочитать имя хоста.]{#linux-listening-services-verify-from-client-a explanation="Имя хоста не проверяет путь по сети."}
::option[Посчитать все слушающие сокеты.]{#linux-listening-services-verify-from-client-b explanation="По их числу нельзя судить о доступе с компьютера сотрудника."}
::option[Отправить разрешённый запрос из сети сотрудников.]{#linux-listening-services-verify-from-client-c .correct explanation="Так вы проверите нужный путь."}
:::

Чтобы проверить, какие сервисы слушают порты на хосте Linux, начните с урока «Аудит слушающих сервисов» в курсе [Безопасность Linux для DevSecOps](https://labex.io/courses/linux-security-for-devsecops).

3. Проверить подключение с нужной стороны клиента.
