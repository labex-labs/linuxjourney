**Межсетевой экран хоста** может разрешать или блокировать входящий трафик по таким признакам, как адрес источника, протокол и порт назначения. Сначала решите, какой трафик нужен сервису.

## Как читать пример правил

Упрощённый набор правил ниже относится к одному хосту. Запись `192.0.2.0/24` с косой чертой обозначает диапазон IPv4-адресов. В примере `192.0.2.44` входит в этот диапазон, а `198.51.100.8` находится за его пределами.

```text
Allow TCP port 443 from any source.
Allow TCP port 22 from 192.0.2.0/24.
Deny other new inbound connections.
```

Порт 443 обслуживает общедоступный сайт. Порт 22 предназначен для сети обслуживания. Правило по умолчанию относится к соединениям, которые не подпадают под два разрешающих правила.

:::single-choice{#linux-host-firewalls-match-trusted-network} Какое новое соединение соответствует правилу для обслуживания?

::option[Соединение TCP с портом 22 из 198.51.100.8.]{#linux-host-firewalls-match-trusted-network-b explanation="Порт подходит, но источник находится за пределами сети управления."}
::option[Соединение TCP с портом 443 из 192.0.2.44.]{#linux-host-firewalls-match-trusted-network-c explanation="Это соединение соответствует правилу для общедоступного сайта."}
::option[Соединение TCP с портом 22 из 192.0.2.44.]{#linux-host-firewalls-match-trusted-network-a .correct explanation="Совпадают и порт назначения, и диапазон адресов источника."}
:::

## Проверка правил и слушающего сокета

Разрешённое соединение всё равно может завершиться ошибкой, если ни одна программа не слушает порт. Точно так же работающий сервис может быть недоступен по пути, который блокирует межсетевой экран. Прочитайте правила и отдельно убедитесь, что сервис слушает нужный порт.

:::single-choice{#linux-host-firewalls-allowed-but-failed} Правило разрешает порт 443, но на хосте его никто не слушает. Что проверить?

::option[Должен ли клиент пользоваться SSH для обслуживания.]{#linux-host-firewalls-allowed-but-failed-a explanation="SSH — другой сервис."}
::option[Слушает ли общедоступный веб-сервис ожидаемый порт.]{#linux-host-firewalls-allowed-but-failed-b .correct explanation="Разрешающее правило межсетевого экрана само по себе не создаёт слушающий сокет."}
::option[Пришёл ли запрос из сети обслуживания.]{#linux-host-firewalls-allowed-but-failed-c explanation="В этом примере правило для сайта принимает запросы из любого источника."}
:::

## Как спланировать безопасную проверку

Проверяя контролируемое изменение, сохраните рабочий путь для обслуживания. Проверьте разрешённый путь из сети обслуживания. Убедитесь, что попытка из согласованной точки вне этой сети не проходит. Для каждой проверки запишите источник, назначение и ожидаемый результат.

:::single-choice{#linux-host-firewalls-verification-pair} Какая пара проверок покажет, действует ли нужное ограничение SSH?

::option[Разрешённая проверка порта 22 из сети обслуживания и извне.]{#linux-host-firewalls-verification-pair-c .correct explanation="Эти запросы проверяют и разрешённый, и запрещённый случаи."}
::option[Два запроса SSH с одной и той же разрешённой машины.]{#linux-host-firewalls-verification-pair-a explanation="Так вы дважды проверите разрешённый случай."}
::option[Два запроса браузера к общедоступной главной странице.]{#linux-host-firewalls-verification-pair-b explanation="Эти запросы проверяют общедоступный порт сайта."}
:::

## Итоги

Теперь вы можете оценивать правила межсетевого экрана вместе с состоянием сервиса.

1. Сопоставить правило с протоколом, назначением и источником.
2. Проверить, что разрешённый сервис слушает нужный порт.
3. Проверить ожидаемый доступ и ожидаемое ограничение.
