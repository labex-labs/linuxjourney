При обслуживании через SSH с каждой стороны соединения нужно ответить на свой вопрос. Клиенту важно знать, к какому серверу он подключился. Серверу нужно определить, разрешён ли вход в учётную запись.

## Как проверить подлинность сервера

Сервер SSH предъявляет **ключ хоста**. Клиент может сравнить его с известным ключом этого хоста. Если ключ неожиданно изменился, проверьте новый ключ через разрешённый независимый источник. Например, сверьтесь с перечнем хостов команды или свяжитесь с ответственным сотрудником по доверенному каналу.

:::single-choice{#linux-ssh-access-unexpected-key} Клиент сообщает, что ключ хоста изменился. Какую проверку провести первой?

::option[Подтвердить ожидаемый новый ключ хоста через доверенный источник.]{#linux-ssh-access-unexpected-key-b .correct explanation="Так вы проверите подлинность сервера, прежде чем полагаться на соединение."}
::option[Попробовать несколько имён пользователей, пока одно не подойдёт.]{#linux-ssh-access-unexpected-key-a explanation="Имя пользователя не подтверждает подлинность сервера."}
::option[Удалить все сохранённые ключи хостов и продолжить.]{#linux-ssh-access-unexpected-key-c explanation="Так вы потеряете сведения о знакомых хостах до выяснения причины изменения."}
:::

## Как проверить доступ пользователя

Пользовательский ключ может подтвердить право клиента входить в учётную запись. Ключ хоста служит для отдельной проверки подлинности сервера. Правила сервера могут ограничивать допустимые учётные записи и способы аутентификации. В учебной сводке указано, что `ops` входит по ключу.

:::single-choice{#linux-ssh-access-distinguish-keys} Что проверяет сервер по пользовательскому ключу ops?

::option[Имя общедоступной веб-страницы.]{#linux-ssh-access-distinguish-keys-b explanation="Содержимое сайта не связано с аутентификацией SSH."}
::option[Подлинность самого сервера.]{#linux-ssh-access-distinguish-keys-c explanation="Для этой проверки клиент использует ключ хоста."}
::option[Подлинность клиента, который пытается войти как ops.]{#linux-ssh-access-distinguish-keys-a .correct explanation="Аутентификация пользователя касается учётной записи, в которую клиент пытается войти."}
:::

## Как сохранить доступ для обслуживания

Перед согласованным изменением правил SSH уточните допустимые учётные записи и способ входа. Проверьте их в отдельном соединении и держите предусмотренный путь восстановления доступным, пока новый вход не пройдёт. Уже открытый сеанс может пережить изменение, даже если новый вход перестал работать.

:::single-choice{#linux-ssh-access-test-new-login} После изменения правил старый сеанс остаётся открытым. Как подтвердить, что сотрудник по-прежнему может войти?

::option[Получить ответ только на ping.]{#linux-ssh-access-test-new-login-a explanation="Ответ по сети не подтверждает успешную аутентификацию SSH."}
::option[Открыть новый разрешённый сеанс SSH с нужной учётной записью и способом входа.]{#linux-ssh-access-test-new-login-c .correct explanation="Так вы проверите правила, которые будут применяться при следующем входе."}
::option[Убедиться, что старый сеанс остаётся открытым без активности.]{#linux-ssh-access-test-new-login-b explanation="Этот сеанс прошёл аутентификацию по прежним правилам."}
:::

## Итоги

Теперь вы можете проверять подлинность участников соединения SSH и правила входа для обслуживания.

1. Подтверждать подлинность сервера по ключу хоста.
2. Отличать эту проверку от аутентификации пользователя.
3. Проверять новое разрешённое соединение после изменения.
