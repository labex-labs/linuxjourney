Состояние маршрутизации Linux определяет, какие следующий переход, интерфейс и источник подходят для IP-назначения. Устаревшее представление `route -n` всё ещё встречается, но `ip route` точнее показывает современные понятия маршрутизации ядра.

## Чтение маршрутов IPv4

Пример вывода:

```text
$ ip -4 route show
default via 192.168.224.2 dev eth0 proto dhcp src 192.168.224.10 metric 100
192.168.224.0/24 dev eth0 proto kernel scope link src 192.168.224.10 metric 100
```

Подключённый маршрут `/24` отправляет совпавшие назначения напрямую через `eth0`. Маршрут по умолчанию использует шлюз следующего перехода `192.168.224.2`. `proto` описывает способ установки маршрута, `src` — предпочтительный источник для совпавшего трафика, а метрика помогает ранжировать другие сопоставимые маршруты.

:::single-choice{#routing-table-via-meaning} Что обозначает `via 192.168.224.2`?

::option[Единственное приложение, которому разрешено использовать маршрут.]{#routing-table-application explanation="Авторизация приложения не кодируется ключевым словом via."}
::option[Шлюз следующего перехода для маршрута.]{#routing-table-next-hop .correct explanation="Пакет помещается в кадр для этого локального маршрутизатора, сохраняя своё IP-назначение."}
::option[Точку подключения файловой системы маршрута.]{#routing-table-mount explanation="Записи маршрутизации относятся к сетевой пересылке, а не файловым системам."}
:::

## Подключённые маршруты и маршруты по умолчанию

Маршрут со `scope link` и без следующего перехода `via` считает префикс непосредственно доступным через интерфейс. Маршрут по умолчанию совпадает с любым адресом, но уступает каждому подходящему более конкретному маршруту.

:::single-choice{#routing-table-connected-route} Как обычно достигается подключённое назначение `scope link`?

::option[Через шлюз по умолчанию, даже когда совпадает подключённый маршрут.]{#routing-table-connected-default explanation="Подключённый префикс конкретнее и не имеет операнда шлюза."}
::option[Преобразованием назначения в DNS-сервер.]{#routing-table-connected-dns explanation="Служба имён не участвует в уже выбранном IP-маршруте."}
::option[Напрямую через указанный интерфейс после разрешения соседа.]{#routing-table-direct .correct explanation="Хост разрешает локальный адрес назначения и создаёт кадр в местном канале."}
:::

## Длина префикса и метрика

Выбор маршрута учитывает правила политик и использует самый длинный подходящий префикс. Метрики ранжируют маршруты внутри подходящих сопоставимых наборов; маршрут по умолчанию с малой метрикой не переопределяет совпавший `/24` только потому, что его число меньше.

:::single-choice{#routing-table-prefix-before-default} Какой маршрут конкретнее совпадает с `192.168.224.50`?

::option[`192.168.224.0/24 dev eth0`]{#routing-table-twenty-four .correct explanation="24-битный совпавший префикс является самым длинным среди перечисленных маршрутов."}
::option[`default via 192.168.224.2`]{#routing-table-default-less-specific explanation="У маршрута по умолчанию длина префикса равна нулю."}
::option[`192.168.0.0/16 via 192.168.224.3`]{#routing-table-sixteen explanation="Он охватывает адрес, но фиксирует меньше битов, чем /24."}
:::

## Правила политик и несколько таблиц

Linux может обращаться к нескольким таблицам маршрутизации согласно политике `ip rule`, основанной на источнике, метке, интерфейсе и других селекторах. Поэтому просмотр только основной таблицы может не показать фактический путь:

```bash
$ ip rule show
$ ip route show table all
```

Сетевые пространства имён и VRF также могут иметь отдельное состояние. Выполняйте проверку в том же контексте, что и затронутый процесс.

:::single-choice{#routing-table-policy-limit} Почему одного `ip route show` может быть недостаточно для объяснения пути приложения?

::option[Правила политик или другое сетевое пространство имён могут выбрать иное состояние маршрутизации.]{#routing-table-policy-context .correct explanation="Фактический поиск зависит от атрибутов пакета и сетевого контекста процесса."}
::option[Таблицы маршрутизации Linux не содержат префиксов назначения.]{#routing-table-no-prefixes explanation="Префиксы назначения являются основными ключами маршрутов."}
::option[Приложения никогда не отправляют IP-пакеты.]{#routing-table-apps-never explanation="Трафик приложений переносится через сетевые и транспортные протоколы."}
:::

## Запрос фактического маршрута

Попросите ядро оценить назначение и необязательный источник:

```bash
$ ip route get 203.0.113.10
$ ip route get 203.0.113.10 from 192.168.224.10
```

Результат прогнозирует локальный поиск в этот момент. Он не отправляет пробный пакет и не доказывает доступность соседа, последующего пути, межсетевого экрана или приложения.

:::single-choice{#routing-table-route-get-limit} Чего не делает `ip route get`?

::option[Не отображает выбранные локальный интерфейс и следующий переход.]{#routing-table-get-does-interface explanation="Это основные поля результата поиска."}
::option[Не оценивает текущую локальную политику маршрутизации для назначения.]{#routing-table-get-does-policy explanation="Команда выполняет поиск маршрута ядром."}
::option[Не доказывает успешную доставку через каждый последующий переход.]{#routing-table-get-not-probe .correct explanation="Это локальный запрос решения, а не сквозная сетевая проба."}
:::

## Итоги

Теперь вы можете читать записи маршрутизации Linux и запрашивать фактическое локальное решение.

1. Отличайте подключённые маршруты от маршрутов через шлюз.
2. Читайте поля префикса, интерфейса, протокола, источника и метрики.
3. Применяйте сопоставление по самому длинному префиксу до сравнения подходящих метрик.
4. Учитывайте таблицы политик, пространства имён и VRF.
5. Рассматривайте `ip route get` как поиск, а не проверку доступности.
