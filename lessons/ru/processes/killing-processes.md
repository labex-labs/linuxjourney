Команда `kill` отправляет сигнал процессу или группе процессов. Её название историческое: запрошенный сигнал может завершить, остановить, продолжить процесс или вызвать определённое приложением действие. До отправки всегда подтверждайте точную цель и изучайте документированное поведение программы для сигналов.

## Запрос нормального завершения

Если указан только PID, `kill` по умолчанию отправляет `SIGTERM`:

```bash
$ kill 12445
```

При явном указании сигнала предпочитайте символическое имя:

```bash
$ kill -TERM 12445
```

Стандартное действие `SIGTERM` — завершение, но программа может перехватить или игнорировать его. Правильно спроектированная служба способна с помощью обработчика прекратить принимать работу, сохранить подходящее состояние и освободить ресурсы приложения. Это возможность, а не гарантия немедленной или успешной очистки.

## Проверка цели

PID могут использоваться повторно, поэтому устаревший PID позднее способен обозначать другой процесс. Проверьте живую цель непосредственно перед действием:

```bash
$ ps -p 12445 -o pid,ppid,user,lstart,stat,cmd
```

Проверьте пользователя, время запуска, команду, родителя, владельца-службу и эксплуатационную роль. Если процессом управляет диспетчер служб, по возможности используйте его команду остановки или перезагрузки, чтобы он сохранил правильное состояние и не перезапустил потомка немедленно.

С учётом правил учётных данных вы можете отправлять сигналы собственным процессам. Для процесса другого пользователя обычно нужны соответствующие привилегии. Не применяйте широкую команду по имени, пока не проверите каждое совпадение.

## Проверка разрешения сигналом ноль

Сигнал номер ноль выполняет проверку ошибок без доставки настоящего сигнала:

```bash
$ kill -0 12445
```

Успех означает, что в этот момент существует процесс с таким PID и вызывающей стороне разрешено посылать ему сигналы. Ошибка неоднозначна: процесс может отсутствовать либо у вызывающей стороны может не быть прав. Проверяйте сообщение и код завершения, а не переводите любую ошибку как «не работает». Это также лишь мгновенная проверка, не устраняющая последующую гонку повторного использования PID.

:::single-choice{#killing-processes-signal-zero}
Что в данный момент устанавливает успешный `kill -0 PID`?

::option[Процесс завершил всю очистку и вышел.]{#killing-processes-zero-exited explanation="Успех указывает на живую доступную для сигналов цель, а не на завершённое прекращение."}
::option[Процесс навсегда сохранит этот PID.]{#killing-processes-zero-permanent explanation="Проверка мгновенна, и после завершения PID может использоваться повторно."}
::option[Процесс существует, и вызывающая сторона может посылать ему сигналы.]{#killing-processes-zero-permitted .correct explanation="Сигнал ноль проверяет наличие цели и авторизацию без доставки обычного сигнала."}
:::

## Эскалация только при необходимости

Если разрешённая цель не завершается после `SIGTERM`, дайте ей подходящее для нагрузки время и выясните причину. Затем, когда принудительное завершение оправданно, отправьте:

```bash
$ kill -KILL 12445
```

`SIGKILL` нельзя перехватить, игнорировать или заблокировать, поэтому программа не может выполнить очистку на уровне приложения. Могут остаться незавершённые транзакции, временное состояние или работа по восстановлению для других компонентов. Используйте его как эскалацию, а не обычный первый шаг.

Другие сигналы имеют смысл только согласно контракту принимающей программы. `SIGHUP` часто запрашивает перезагрузку конфигурации, но некоторые программы сохраняют его стандартное завершающее действие. `SIGSTOP` приостанавливает без очистки, а `SIGCONT` возобновляет остановленный процесс.

:::single-choice{#killing-processes-kill-tradeoff}
Каков основной эксплуатационный недостаток `SIGKILL`?

::option[Его может обработать только владелец процесса.]{#killing-processes-kill-owner-handler explanation="Ни один целевой процесс не может установить обработчик SIGKILL."}
::option[Он приостанавливает процесс, но никогда не завершает его.]{#killing-processes-kill-pauses explanation="SIGSTOP приостанавливает, а SIGKILL завершает."}
::option[Он не даёт программе возможности выполнить очистку на уровне приложения.]{#killing-processes-kill-no-cleanup .correct explanation="Ядро принудительно завершает процесс без вызова пользовательского обработчика сигнала."}
:::

Практикуйтесь выбирать сигналы только для запущенных вами процессов в изолированной среде. Лаборатория [Управление и мониторинг процессов Linux](https://labex.io/ru/labs/comptia-manage-and-monitor-linux-processes-590864) предоставляет контролируемый процесс проверки и завершения.

## Итоги

Теперь вы можете отправлять сигналы процессам осознанным и проверяемым способом.

1. До действия подтверждайте живую цель и её супервизор.
2. Используйте `SIGTERM` как обычный запрос завершения.
3. Интерпретируйте сигнал ноль как мгновенную проверку существования и прав.
4. Оставляйте `SIGKILL` для оправданной эскалации после исследования.
