Обычное приложение обращается к stub resolver ОС, который учитывает локальную политику name service и отправляет рекурсивный запрос настроенному резолверу. Тот обходит иерархию только при отсутствии действительного ответа в кеше.

## Локальная политика и кеш

Системный резолвер может в настроенном порядке обращаться к `/etc/hosts`, DNS и другим источникам. Поисковые суффиксы превращают короткое имя в несколько кандидатов. Рекурсивный резолвер проверяет положительный и отрицательный кеш до внешних запросов.

:::single-choice{#dns-process-cache-first} Почему рекурсивный резолвер может не обращаться к авторитетному серверу?

::option[DNS требует сначала локально отклонить каждый запрос.]{#dns-process-requires-failure explanation="Резолвер может сразу ответить из кеша."}
::option[У него есть ещё действительный кешированный ответ.]{#dns-process-valid-cache .correct explanation="Кеширование избегает повторного обхода иерархии до истечения срока записи."}
::option[Авторитетные серверы принимают только Ethernet-кадры клиентов.]{#dns-process-authoritative-ethernet explanation="DNS работает поверх IP-транспортов через маршрутизируемые сети."}
:::

## Запрос корневого сервера

При промахе кеша резолвер может спросить корневой сервер. У DNS root 13 именованных личностей серверов A–M, обслуживаемых множеством физических экземпляров через anycast и другие отказоустойчивые схемы. Обычно ответ направляет к авторитетным серверам нужного TLD, а не возвращает конечный адрес хоста.

:::single-choice{#dns-process-root-response} Что корневой сервер обычно возвращает для незакешированного `www.example.com`?

::option[Referral к серверам домена верхнего уровня `com`.]{#dns-process-root-referral .correct explanation="Иерархия делегирует ответственность вместо хранения каждой конечной записи в корне."}
::option[Веб-страницу с `www.example.com`.]{#dns-process-root-webpage explanation="DNS возвращает ресурсные записи, а не содержимое приложения."}
::option[Ethernet MAC-адрес назначения.]{#dns-process-root-mac explanation="MAC-адреса разрешаются на локальном канале, а не через иерархию DNS."}
:::

## Referral TLD и авторитетного сервера

Резолвер спрашивает авторитетный сервер `com`, который возвращает делегированные серверы `example.com`. Referral может содержать glue-адреса, если сервер с именем внутри дочерней зоны иначе нельзя достичь. Затем резолвер спрашивает авторитетный сервер нужной записи.

:::single-choice{#dns-process-glue-purpose} Какую проблему решает DNS glue?

::option[Шифрование HTTP после разрешения DNS.]{#dns-process-glue-http explanation="За шифрование содержимого отвечает TLS или другая безопасность приложения."}
::option[Выбор самого быстрого порта Ethernet-коммутатора.]{#dns-process-glue-switch explanation="Glue — адресные данные делегирования, а не политика канальной пересылки."}
::option[Достижение in-bailiwick сервера без циклического разрешения.]{#dns-process-glue-reachability .correct explanation="Родитель передаёт адрес, необходимый для связи с сервером, названным внутри дочерней зоны."}
:::

## Псевдонимы и типы записей

Ответ может содержать CNAME, требующий поиска другого имени, или записи приложения, ведущие к дополнительным запросам. Запрос `A` возвращает только IPv4-записи и данные цепочки; IPv6 получает отдельный `AAAA`. Итоговый ответ имеет статус `NOERROR`, `NXDOMAIN` или `SERVFAIL` с разным смыслом.

:::single-choice{#dns-process-nxdomain-meaning} Что сообщает `NXDOMAIN`?

::option[По авторитетному результату запрошенное доменное имя не существует.]{#dns-process-name-does-not-exist .correct explanation="Это отличается от существующего имени, у которого просто нет запрошенного типа."}
::option[Имя существует и всегда имеет пустую A-запись.]{#dns-process-empty-a explanation="Существующее имя без запрошенных данных обычно даёт no-data, а не NXDOMAIN."}
::option[Резолвер достиг максимального размера Ethernet-кадра.]{#dns-process-frame-size explanation="Статус относится к существованию имени."}
:::

## Проверка, кеш и использование приложением

Валидирующий рекурсивный резолвер использует подписи DNSSEC и цепочку доверия для проверки целостности записей или аутентифицированного отрицания. DNSSEC не шифрует запросы и не доказывает надёжность приложения по адресу.

Резолвер кеширует результат по TTL и возвращает stub. Приложение выбирает адрес и применяет собственные сетевые и защитные протоколы.

:::single-choice{#dns-process-dnssec-limit} Чего не предоставляет проверка DNSSEC?

::option[Целостности и аутентификации происхождения подписанных данных.]{#dns-process-dnssec-does-integrity explanation="Это основные цели DNSSEC."}
::option[Аутентифицированного отрицания подписанных отсутствующих данных.]{#dns-process-authenticated-denial explanation="Механизмы подписанного отрицания могут это обеспечить."}
::option[Конфиденциальности DNS-запроса и ответа.]{#dns-process-no-confidentiality .correct explanation="Для шифрования нужен отдельный защищённый транспорт вроде DoT или DoH."}
:::

## Итоги

Теперь вы умеете прослеживать рекурсивный поиск DNS от локальной политики до кешированного результата.

1. Сначала проверять локальные источники и кеш резолвера.
2. Следовать referral корня и TLD.
3. Использовать glue для достижения делегированных серверов.
4. Отличать псевдонимы, no-data и несуществующие имена.
5. Отделять целостность DNSSEC от конфиденциальности транспорта.
