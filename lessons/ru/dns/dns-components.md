DNS отделяет обращённую к клиенту рекурсию от авторитетной публикации. Понимание границы не позволяет принять кешированный ответ за владельца зоны.

## Stub- и рекурсивные резолверы

Stub resolver приложения или ОС отправляет запрос настроенному рекурсивному резолверу. Тот возвращает итоговый ответ, ошибку или результат referral после использования кеша и при необходимости итеративных запросов. Флаг authoritative answer появляется лишь когда отвечающий сервер авторитетен для данных; сама рекурсия авторитетности не даёт.

:::single-choice{#dns-components-recursive-role}
Что рекурсивный резолвер делает для stub-клиента?

::option[Получает итоговый DNS-результат через кеш и другие серверы имён.]{#dns-components-recursive-result .correct explanation="Клиент передаёт рекурсивной службе многошаговую работу поиска."}
::option[Заменяет каждый сетевой маршрутизатор на пути пакета.]{#dns-components-replaces-router explanation="Разрешение имён и IP-маршрутизация независимы."}
::option[Становится авторитетным для каждой кешированной записи.]{#dns-components-cache-authority explanation="Кешированные данные сохраняют источник авторитетности; резолвер не становится владельцем зоны."}
:::

## Авторитетные серверы имён

Авторитетный сервер отвечает из данных зон, за которые ответственен. Зона должна иметь несколько синхронизированных авторитетных серверов с независимыми отказами. Сервер, предназначенный только для авторитетных ответов, не обязан выполнять рекурсию для произвольных клиентов.

:::single-choice{#dns-components-authoritative-role}
Что делает сервер авторитетным для зоны?

::option[Он однажды запросил зону у публичного резолвера.]{#dns-components-once-queried explanation="Запрос или кеширование не наделяет авторитетностью."}
::option[Он обслуживает данные зоны согласно делегированию и конфигурации.]{#dns-components-serves-zone .correct explanation="Авторитетность происходит из делегирования и загруженной зоны, а не кешированной копии."}
::option[Он быстрее всех ответил на ping.]{#dns-components-fastest-ping explanation="Время ICMP не определяет авторитетность DNS."}
:::

## Зоны и хранение данных

Зона — административно обслуживаемая часть namespace DNS. Она начинается в apex и может делегировать дочерние зоны. Данные могут находиться в текстовом zone file, генерироваться из базы, загружаться API или синтезироваться; «файл зоны» не является обязательной физической реализацией.

Apex обычно имеет SOA и набор NS. Делегирование у родителя указывает авторитетные серверы дочерней зоны и иногда glue-адреса для достижения in-bailiwick имён серверов.

:::single-choice{#dns-components-zone-meaning}
Что такое DNS-зона?

::option[Административно обслуживаемая часть namespace.]{#dns-components-admin-portion .correct explanation="Она содержит записи и делегирования независимо от способа хранения."}
::option[Обязательный одиночный текстовый файл на каждом клиенте.]{#dns-components-client-file explanation="Авторитетные реализации используют разные хранилища, а клиенты не держат все зоны."}
::option[Широковещательный домен Ethernet с VLAN.]{#dns-components-vlan explanation="DNS-зоны и сегменты канального уровня независимы."}
:::

## Поля ресурсной записи

Запись имеет owner name, TTL, class, type и типоспецифичные RDATA. Например:

```text
www.example.com.  300  IN  A  192.0.2.25
```

Owner — `www.example.com.`, TTL — 300 секунд, класс — Internet, тип — IPv4-адрес, RDATA — адрес. Пропуск полей и относительные имена в синтаксисе zone file требуют внимательного учёта origin.

:::single-choice{#dns-components-mx-type}
Какой тип публикует приоритет и имена mail exchanger?

::option[`A`]{#dns-components-a explanation="A хранит IPv4-адрес."}
::option[`NS`]{#dns-components-ns explanation="NS указывает авторитетные серверы имён."}
::option[`MX`]{#dns-components-mx .correct explanation="RDATA MX содержит приоритет и имя почтового обменника."}
:::

## TTL и отрицательное кеширование

Положительные записи ограничивают кеш через TTL. Отрицательные ответы, например доказанное отсутствие имени, также кешируются по правилам SOA. Снижение TTL перед изменением влияет только на записи, полученные после того, как кеши увидят новое значение; ранее закешированный длинный TTL действует до истечения.

:::single-choice{#dns-components-lower-ttl-timing}
Зачем снижать TTL задолго до плановой смены адреса?

::option[TTL меняет Ethernet MTU сервера.]{#dns-components-ttl-mtu explanation="Срок кеша и размер пакета канального уровня не связаны."}
::option[Низкий TTL гарантирует исправность нового приложения.]{#dns-components-ttl-health explanation="Он влияет на кеширование, а не корректность службы."}
::option[Старым кешам нужно время, чтобы истекли записи с прежним длинным TTL.]{#dns-components-old-cache-expiry .correct explanation="Изменение авторитетных данных не может задним числом сократить остаток уже закешированной записи."}
:::
