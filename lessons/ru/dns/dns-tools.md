Диагностика DNS начинается с определения проверяемого уровня. Инструменты системного резолвера учитывают локальные файлы и политику, а `dig` и `nslookup` отправляют DNS-запросы и могут напрямую обращаться к конкретному серверу.

## Проверка системного резолвера

Используйте обычный системный путь службы имён хостов:

```bash
$ getent ahosts www.example.com
```

На хосте с systemd-resolved проверьте серверы отдельных соединений, поисковые домены и состояние протоколов:

```bash
$ resolvectl status
$ resolvectl query www.example.com
```

Приложение всё равно может использовать собственную библиотеку резолвера или прокси, поэтому при расхождении результатов воспроизведите запрос через само приложение.

:::single-choice{#dns-tools-system-resolver}
Какая команда задействует настроенный системный путь службы имён?

::option[Только `dig @SERVER NAME`.]{#dns-tools-dig-direct explanation="Dig отправляет DNS-запрос и обычно не читает сопоставления из файла hosts."}
::option[`ip link set down`]{#dns-tools-link-down explanation="Эта команда нарушает работу интерфейса вместо проверки разрешения имён."}
::option[`getent ahosts NAME`]{#dns-tools-getent .correct explanation="Она может учитывать `/etc/hosts`, DNS и другие источники Name Service Switch."}
:::

## Запросы с помощью dig

Укажите имя и тип записи:

```bash
$ dig www.example.com A
$ dig www.example.com AAAA
$ dig example.com MX
```

Вывод показывает ответивший сервер, статус, флаги, вопрос, ответ, авторитетные и дополнительные данные, время запроса и сведения о транспорте. Параметр `+short` удобен для сценариев, но скрывает доказательства, необходимые для диагностики.

:::single-choice{#dns-tools-record-type}
Какой запрос запрашивает записи IPv6-адресов?

::option[`dig NAME AAAA`]{#dns-tools-aaaa .correct explanation="Записи AAAA содержат IPv6-адреса."}
::option[`dig NAME MX`]{#dns-tools-mx explanation="MX запрашивает записи почтовых серверов."}
::option[`dig NAME PTR` с прямым именем.]{#dns-tools-ptr-forward explanation="PTR обычно запрашивают по имени обратного разрешения."}
:::

## Выбор сервера

Явно укажите резолвер или авторитетный сервер:

```bash
$ dig @192.0.2.53 www.example.com A
```

Чтобы отличить кеш от авторитетного источника, сравнивайте настроенный рекурсивный резолвер, второй одобренный резолвер и каждый авторитетный сервер. Статус `NOERROR` может не содержать запрошенного ответа; `NXDOMAIN` означает, что запрошенное имя не существует, а `SERVFAIL` — что сервер не смог завершить запрос.

:::single-choice{#dns-tools-noerror-empty}
Может ли при `NOERROR` раздел ответа быть пустым?

::option[Да, если имя существует, но не имеет записей запрошенного типа.]{#dns-tools-noerror-nodata .correct explanation="Статус и количество ответов нужно интерпретировать вместе."}
::option[Нет, этот статус гарантирует хотя бы одну адресную запись.]{#dns-tools-noerror-always-answer explanation="Имя может существовать без данных запрошенного типа."}
::option[Нет, пустой ответ всегда означает ошибку Ethernet.]{#dns-tools-empty-ethernet explanation="Корректный ответ без данных объясняется семантикой DNS, а не формированием кадров канального уровня."}
:::

## Проверка рекурсии и авторитетности

Флаг `rd` в запросе требует рекурсии; `ra` в ответе сообщает, что сервер её предоставляет. `aa` означает авторитетность ответа. Запрашивайте авторитетный сервер с `+norecurse`, чтобы не спутать рекурсивный кеш с данными обслуживаемой зоны.

Команда `dig +trace NAME` выполняет собственный итеративный обход, начиная с корневых подсказок. Её результат может отличаться от производственного резолвера, потому что она обходит его кеш, пересылку, политику, проверку DNSSEC и сетевое расположение.

:::single-choice{#dns-tools-aa-flag}
Что означает флаг ответа `aa`?

::option[В запросе использованы два одинаковых IPv4-адреса.]{#dns-tools-two-addresses explanation="Флаг не связан с количеством ответов или семейством адресов."}
::option[Ответ зашифрован учётными данными приложения.]{#dns-tools-aa-encrypted explanation="Флаги DNS не устанавливают зашифрованный транспорт."}
::option[Ответ является авторитетным.]{#dns-tools-authoritative-answer .correct explanation="Ответивший сервер заявляет свою авторитетность для данных ответа."}
:::

## Проверка обратных запросов и TCP

Используйте `-x`, чтобы создать обратный PTR-запрос:

```bash
$ dig -x 192.0.2.25
```

При исследовании усечения, передачи зон или различий межсетевого экрана проверьте DNS через TCP:

```bash
$ dig +tcp @192.0.2.53 example.com SOA
```

Современный DNS может использовать UDP или TCP на порту 53; там, где они необходимы, нужно разрешить оба транспорта. Флаг усечения в UDP-ответе побуждает соответствующие стандарту клиенты повторить запрос через подходящий транспорт.

:::single-choice{#dns-tools-tcp-test}
Что изменяет `dig +tcp`?

::option[DNS-запрос отправляется через TCP вместо попытки через UDP по умолчанию.]{#dns-tools-use-tcp .correct explanation="Это помогает выявить фильтрацию транспорта и ответы, которым требуется более крупный надёжный поток."}
::option[Запрашиваются только записи имён служб TCP.]{#dns-tools-tcp-records explanation="Тип DNS-записи указывается отдельно."}
::option[Конфигурация резолвера сервера изменяется навсегда.]{#dns-tools-tcp-persistent explanation="Запрос не редактирует настройки сервера."}
:::

## Итоги

Теперь вы можете выбирать инструмент DNS в соответствии с исследуемым уровнем разрешения имён.

1. Использовать `getent` для настроенного пути системного резолвера.
2. Вызывать `dig` с явно указанными типами записей и серверами.
3. Совместно интерпретировать статус, флаги, разделы и ответивший сервер.
4. Отделять рекурсивный кеш от авторитетных данных.
5. Проверять обратные запросы и оба необходимых транспорта DNS.
